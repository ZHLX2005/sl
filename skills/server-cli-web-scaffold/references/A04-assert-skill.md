# A04 · Skill 创建的前期架构考虑

> 归属主文档 [[server-cli-web-scaffold]]。**写代码前先写 skill；写完 skill 再写代码。**
>
> 这一节插在 `[[A01-bootstrap-serve-first]]`（定骨架）之后、`[[A05-state-storage]]`（接状态）之前——因为它要回答的是"你这个项目到底要被谁调用、怎么被调用"，决定所有后续 action 的形态。

## 一句话原则

**skill 不是文档，是产品的一部分。** 项目初始化 = `SKILL.md` + `references/` 一个思想文档同时落地。两者皆缺，等于把这个项目对 agent 设为不可用。

| 时刻 | 该交付什么 | 缺了会怎样 |
| --- | --- | --- |
| 阶段 1 写完骨架 | `SKILL.md` + `references/00-设计思想.md`（或等价骨架级文档） | agent 拿到这个项目不知道它是干啥的，触发词写不出 |
| 每个新功能域首次落地 | 该域对应的 `references/<域>.md`（场景级 SOP） | agent 能跑命令但不知道怎么用、用错了没人救 |
| 状态/存储/发版契约稳定时 | 对应 `references/<编号>-<主题>.md` | 同上，只是触发频率更低 |

> **"思想文档"是骨架级**——讲架构、边界、不变量、路由原则。任何"什么时候读它"由主文档的路由表决定，不由 agent 自由发挥。

## 思想文档的最小骨架（初始化即写）

新建一个项目时，**`SKILL.md` 和 `references/` 必须同时存在**。下面这个骨架不是装饰，是为了让 agent 在第一次接触项目时不靠猜：

### SKILL.md 必含

- **触发词清单**（一句话能描述 + 关键词 5-10 个）
- **核心不变量**（3 条以内，每条用 1-2 个例子说明"违反会怎样"）
- **核心命令/动作表**（短表，链接到 references 详读）
- **什么时候不用**（反例，避免误触发）

### references/00-思想文档 必含

按本 skill 的编号约定命名为 `00-<主题>.md` 或 `00-设计思想.md`。必含五段：

1. **驱动关系图**（一张 ASCII / Mermaid，说明谁依赖谁）
2. **分层与依赖方向**（哪一层只能依赖哪一层；为什么）
3. **关键不变量**（每条配 1 个"违反会怎样"的真实场景）
4. **失败 vs 业务结果**（沿用主文档第 3 条不变量的二分法）
5. **错误案例表**（3-5 条"踩过的坑"，每条给正确做法）


### assets 与项目文档的分工（**最容易写错的一步**）

`assets/<skill>/` 会随 `npm publish` 发到**用户机器**上，被**用户侧的 agent**加载。
所以它的内容判据不是「重不重要」，而是：

> **用户装完这个包，他的 agent 会在什么场景下需要这段知识？**

答不上来的，就**不属于 assets**——哪怕它对项目本身至关重要。

| 内容 | 放哪 | 判据 |
| --- | --- | --- |
| 命令怎么调、参数怎么传、语义陷阱、错误码怎么处理 | `assets/<skill>/` | 用户侧 agent 天天要用 |
| 数据模型、存储位置、导出/回滚怎么用 | `assets/<skill>/` | 用户要理解自己的数据在哪 |
| **改这个项目本身**：加功能域要碰哪几处、分层与 lint 怎么改、新增 ref 怎么编号 | **项目仓库**（`README.md` / `CONTRIBUTING`） | 只有仓库开发者会做，用户手上没有 `src/` |
| 可复用的**骨架**规范（本 skill 自己） | 脚手架 skill | 下一个项目也用得上 |

**写错的三种方向**：

- ✗ **assets 里塞开发手册**：用户侧 agent 永远读不到 `src/modules/`，这段知识对它等于噪音；
  写的人却因此以为「已经文档化了」，而项目仓库那边反倒空着。
  实测反例：某项目的 `references/40-extend.md` 整篇是「加栏目模板 / 加功能域要碰的 N 处」，
  属于项目开发规范而非使用方法，已从 assets 删除、内容归位到项目 `README.md` 指向的脚手架 ref。
- ✗ **只写进 assets，项目仓库不写**：从 clone 开始接手的人拿不到它，因为 `assets/` 里那份
  是给 agent 看的、按「怎么用」组织的，不是给开发者看的。
- ✗ **assets 里引用机器级/项目级路径或开发参考出处**：assets skill 是**全局**的——装到任何
  机器、在任何项目里被加载，它不能假设读者机器上有任何特定目录、特定仓库。
  两种典型：(a) 给方法标出处「结构参照 xx 项目 `packages/core/...`」「参见 xx 仓库 `codex-rs/...`」——
  用户机器上没有这些仓库，引用全是死链，且 skill 也没法执行「去参照」这个动作；
  (b) 把**某个项目的本地目录约定**当通用路径写进流程（如 `.claude/repo/_self/`、`docs/superpowers/specs/`）——
  那是项目文档级约定，换了项目就不存在。
  正确做法：参照研究在**开发期**完成并消化，进 assets 的只有自包含的原则与结论；
  流程里涉及「文档写到哪」时，写「当前项目的文档目录（如 `docs/`，项目已有约定就用现有的）」，
  绝不硬编码任何具体项目的路径。被依赖的全局 skill 自身怎么组织输出（如 `superpowers:writing-plans`
  把计划存哪），由那个 skill 自己的规范决定，本 skill 不转述其路径。

**自检**：写完一个 ref，问两个问题——

1. 「这条命令/这个方法，用户装完包之后会在什么时候需要它？」
   若答案是「他要改这个包的源码时」——那就该挪出 assets。
2. 「文中引用的每个路径/仓库，用户的机器上（任意项目里）存在吗？」
   若答案是「只有我开发机上 / 只有某个特定项目里才有」——删掉引用，
   把知识改写成不依赖引用的自包含表述。

### 场景级 ref 按需扩展

每个功能域、每个稳定下来的工程契约，对应一个独立 ref，编号按本 skill 的 `NN-<主题>.md` 约定：

- `02-web-panel`（视觉规范）/ `03-cli-surface`（对外契约）/ `05-state-storage`（存储约定）—— 这些是**本骨架的默认场景**，不是这个 skill 创建的项目该有的。
- 一个具体项目会有自己的 `references/<域>.md`，描述该域的命令、参数、典型坑。
- **扩展原则**：先看是否已有 ref 可加节，没有再新建 ref——与 key_board 的「路由优先级」一致。

## 为什么这个顺序不能颠倒

| 顺序 | 后果 |
| --- | --- |
| ✅ 先 skill 后代码 | skill 写出来的就是「项目想被怎么用」，代码去匹配契约 |
| ❌ 先代码后 skill | skill 变成「给现有代码补使用说明」——必然遗漏反向 case，且随代码漂移 |

第一条命中的，是这条原则的**最强反模式**：写完代码再来补 skill，缺什么补什么，没人会主动暴露"我设计错了"的地方——因为代码已经按错的设计跑起来了。skill 沦为文档副作用，而不是契约源。

## SKILL.md 的触发词怎么写（自检）

写完 SKILL.md 的 `description` 字段后，对照下面 4 条自检，**任一不达标就别提交**：

- [ ] 用「当用户……时使用」开头（症状描述，非流程描述）
- [ ] 5-10 个触发词（命令动词、主题词、典型场景）
- [ ] 明确写了 1-2 个「不适用」的反例
- [ ] `name` 是小写连字符（`<项目>-<角色>` 形态），不带版本号

> 反例：`description: 总结成 skill` —— 这不是触发词，是 skill-creator 的触发词，且没有症状也没有反例。

## 与 key_board 的协作

如果你这个项目本身是个"工具生成器"或"skill 分发器"，那么创建这个项目**前**应先用 [[key_board]] 走 `references/C01-创建新skill.md` 的 SOP；创建这个项目**时**再按本 ref 的最小骨架落地 skill。这样 skill 既符合 key_board 的元规范，又符合本骨架的工程契约。

## 错误案例

| 错误操作 | 实际后果 | 正确做法 |
| --- | --- | --- |
| 项目初始化只写 `bin/` 和 `package.json`，skill 留到发版前补 | agent 在发版前不会用这个项目——所有"脚手架效果"打折到 0；补的时候容易写错触发词 | 阶段 1 就把 `SKILL.md` + `references/00-思想文档.md` 一起交付 |
| 思想文档里塞场景级 SOP（"怎么调 serve"） | 思想文档变长；场景级内容散落多地，按主题找找不到 | 思想文档只讲"为什么"；场景进独立 ref；路由表统一索引 |
| 触发词只写命令动词（"serve / install"） | agent 接到"帮我建个本机工具"这种自然语言时识别不到 | 触发词至少含 1 个**主题词**（"管理面板 / 脚手架 / 本机工具"） |
| 一个项目一个 skill，但反过来所有项目共用一个 skill | agent 分不清"这个项目是干什么的"和"这个脚手架是干什么的"——前者项目级，后者骨架级 | 骨架级 skill 与项目级 skill 分开；项目级 skill 在项目自己的 `assets/<skill>/` 下 |
| 把「改这个项目本身」（加功能域要碰哪几处、lint 怎么改）写进 `assets/<skill>/` | 用户侧 agent 手上没有 `src/`，这段知识对它永远用不上；而真正需要它的人（仓库开发者）在项目仓库里找不到 | assets 只回答「**怎么用**」；开发规范归位到项目 `README.md` / 脚手架 skill |
| 在 assets skill 里写开发参考出处（「结构参照 xx 源码路径」）或项目本地目录约定（`.claude/repo/_self/`、某插件的项目内路径） | assets 是全局 skill：用户机器上没有那些仓库、那个项目里没有那些目录，引用全是死链，skill 也无法执行「去参照」动作 | 参照研究开发期完成并消化成自包含原则；涉及「写到哪」一律写「当前项目的文档目录，项目已有约定就用现有的」；被依赖 skill 的输出路径由它自己决定 |
| skill 写完不跑 `skill-creator` 的触发词评估 | 写的时候自我感觉良好，实际触发率 10% | 写完跑一次评估，按数据调描述 |

### [2026-10-11] key_board 操作教训

> 本 ref 是全局 skill：操作教训只记**通用模式**，不落具体项目名/项目路径——具体案例细节归项目仓库与操作者自己的记录。

| 错误操作 | 实际后果 | 正确做法 |
|---------|---------|---------|
| 给某 skill 写新 ref 时，把参照研究的来源（外部项目源码路径）写成正文引用，还做了「参照实现」对照表 | 用户装的全局 skill 里全是死链引用——用户机器上没有这些仓库；知识被包装成「文献综述」而非可执行要领，被用户指出后才删除改写 | 参照研究是开发期动作：研究完成后只把消化的原则写进 assets，出处留在项目仓库的开发文档/提交说明里 |
| 扫描时把某 ref 里的 `.claude/repo/_self/`、某插件的项目内 specs 路径判为「用户自己生态的约定，不算违规」 | 被用户纠正：assets 全是全局 skill，项目文档级目录约定同样不能进——「如…或…」的软化措辞不改变引用了特定项目路径的事实 | 判据只有一条：这个路径在**任意机器的任意项目**里都存在吗？不存在就改写成「当前项目的文档目录（如 `docs/`，项目已有约定就用现有的）」；判断不了就报给用户，不自行豁免 |
| 本 ref 早已写明 assets 判据，实际写 assets 时依然违规 | 规范存在 ≠ 被执行；写的时候凭「刚研究完、出处很自然要带上」的惯性落笔 | 写 assets 每写完一个 ref，当场跑「两个自检问题」（见上文）；把自检做成写完后的固定动作，而不是靠事后回忆规范 |
| 把含具体项目名/项目案例的操作教训原样记进全局 ref | 全局 skill 被塞进项目级细节，在其他项目加载时成为噪音，违反本 ref 自己的判据 | 教训先 genericize（项目名 → 「某项目/某 skill」，路径 → 通用形态）再入全局 ref；具体案例留在项目仓库或操作者本地记录 |
