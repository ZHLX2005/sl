# A04 · 客户侧 skill（assert-skill）：只讲怎么用

> 归属主文档 [[server-cli-web-scaffold]]。**写代码前先写 skill；写完 skill 再写代码。**
>
> 插在 [[A01-bootstrap-serve-first]] 之后、[[A05-state-storage]] 之前：先回答“这个项目要被谁用、怎么用”，再决定 action 与存储的形态。

## 一、先定读者：客户，不是开发者

**assert-skill = 随包分发、装到客户机器上的 skill（`assets/<skill>/`）。**

> **客户侧 agent：装完包后只有 CLI、Web 面板和自己的数据；没有源码、没有构建链、没有开发环境，也不需要知道这个项目是怎么开发的。它只讲解“怎么用”。**

| 读者 | 手上有什么 | 没有什么 | 该读哪里 |
| --- | --- | --- | --- |
| 客户侧 agent | 已安装的 CLI / 面板、自己的数据、`help --json` | 源码、devDependencies、仓库、构建命令 | `assets/<skill>/`（本 ref 管的产出） |
| 仓库开发者 | 源码、开发环境、测试 | — | 项目 `README.md` / `docs/` / 本脚手架 skill |
| 脚手架开发者 | 本 skill | — | 本 skill 的 A/B 序列 |

**一句话判据：这句话客户装完包之后能执行吗？** 不能，就不属于 assert-skill。

## 二、内容边界：只写“怎么用”，不写“怎么开发”

| 内容 | 放哪 | 理由 |
| --- | --- | --- |
| 命令、参数、flag、典型流程、输出 | `assets/<skill>/` | 客户直接执行 |
| 数据在哪、怎么备份 / 导出 / 恢复 | `assets/<skill>/` | 客户要管理自己的数据 |
| 错误码、失败后的处理、限制与不适用场景 | `assets/<skill>/` | 客户要自己排障 |
| 源码结构、模块分层、lint、如何加功能、如何发版 | 项目 `README.md` / `docs/` | 客户没有 `src/`，也不改项目 |
| 架构思想、设计取舍、内部来源 | 项目 `docs/` / 本 skill | 客户不需要知道实现 |

硬规则：

- assets 里不出现 `src/...`、模块名、`pnpm dev/test/build`、lint 规则、内部包名。
- 不写“改这个项目要碰哪几处”“加功能域要改几处”。
- 不引用作者机器上的路径、仓库或来源出处。
- **A01 例外**：第一本 ref 固定是 `A01-设计思想和解决问题和场景.md`，它讲“解决什么问题、适合什么场景、设计思想（只保留影响用法的部分）”，仍属客户视角；**不要**把它写成项目架构/分层文档。
- 实现架构、模块分层、lint、构建与发版写进项目仓库的 `docs/`（或 `README.md`），不要塞进 assets。
- 客户需要的“为什么”只保留影响用法的那部分。例如“数据存在 `~/<项目名>/`，删除前先备份”可以写；“为什么用原子写”不写。

## 三、交付节奏：阶段 1 起，功能落地即补

| 时刻 | 该交付什么 | 缺了会怎样 |
| --- | --- | --- |
| 阶段 1 骨架完成 | `assets/<skill>/SKILL.md` + `references/A01-设计思想和解决问题和场景.md` | agent 不知道这个项目能干什么、什么时候该用 |
| 首次上手流程稳定 | A 序列 ref（如 `A01-快速开始.md`、`A02-日常操作.md`） | 新客户要自己摸索 |
| 每个功能域首次落地 | 该域的用法 ref（B 序列 `B01-<功能域>.md`） | agent 能跑命令，但不知道怎么组合、边界在哪 |
| 数据 / 错误 / 排障契约稳定 | C 序列 ref（`C01-数据与备份.md`、`C02-错误与排障.md`） | 出问题只能猜 |

> 阶段 1 不要求把所有 ref 写全；但 `SKILL.md` 与 A01 必须先落地，且后续每加一个功能域同步补用法 ref。
> 第一本 ref 的文件名就是 `A01-设计思想和解决问题和场景.md`——不是 `00-设计思想.md`，也不是纯实现架构文档。

### A01 必含（仍以客户为读者）

1. **解决什么问题**：客户现在的痛点、这个工具改变了什么。
2. **适用 / 不适用场景**：什么时候该用、什么时候不该用。
3. **设计思想**：只写影响用法的原则（如“CLI 与面板同源，Web 能做的 CLI 都能做”），不写源码分层与实现取舍。
4. **一条典型路径**：从安装到完成第一个任务，命令 + 预期输出。
5. **数据与边界**：数据在哪、工具不做什么。

> A01 不是架构文档。源码结构、模块分层、lint、构建/发版命令属于项目仓库 `docs/`，不属于 assets。

## 四、标准序列：A/B/C + 两位序号

assert-skill 的 ref 按**客户使用路径**分序列，文件命名 `<序列字母><两位序号>-<主题>.md`：

| 序列 | 类别 | 回答什么 | 例子 |
| --- | --- | --- | --- |
| A | 上手与日常使用 | 第一次怎么开始、每天怎么用 | `A01-快速开始.md`、`A02-日常操作.md` |
| B | 按功能域的用法 | 某类任务怎么做、参数怎么传 | `B01-<功能域>.md`、`B02-<功能域>.md` |
| C | 数据、错误与排障 | 数据在哪、出错怎么办、限制是什么 | `C01-数据与备份.md`、`C02-错误与排障.md` |

规则：

- 用 **A01 / A02 / B01 / B02 / C01**，不用裸 `00-`、`01-`、`NN-`；编号同时承载“序列”和“顺序”两层信息。
- 从 `01` 起。单成员序列不建 `00`；确实需要序列入口时才建 `<X>00-...`，且只放序列内路由，不放场景 SOP。
- 新增主题：先判断属于 A/B/C 哪条使用路径；已有 ref 能加节就加节，没有才新建——与 key_board 的「路由优先级」一致。
- `SKILL.md` 必须有路由表：**代号 / 什么时候读 / 文件**。主文档只做路由，场景细节一律放 ref。
- ref 数量很少时也至少用 `A01`，不要因为只有一条就退回纯数字命名。

> 命名依据：key_board `references/X02-ref路由优化.md`。单成员序列可跳过 `00`，但动作 ref 从 `01` 起。

## 五、SKILL.md 最小骨架

### SKILL.md 必含

- **触发词清单**（“当用户……时使用” + 5-10 个关键词）
- **定位一句话**（这个工具解决什么问题）
- **核心命令 / 动作表**（短表，链接到 ref 详读）
- **数据位置**（客户需要知道自己的数据在哪）
- **什么时候不用**（反例，避免误触发）
- **ref 路由表**（A/B/C 序列 → 什么时候读 → 文件）

### SKILL.md 不该有

- 源码目录结构、模块分层、lint 规则、开发命令
- “如何改这个项目”“如何加功能域”“如何发版”
- 内部设计取舍与架构图（这些属于项目 `docs/`）

## 六、写完每条 ref 的自检

1. 「客户装完包，只有 CLI / 面板 / 数据，这句话他能执行吗？」
   不能 → 这条不属于 assets。
2. 「里面有没有 `src/`、模块名、lint、`pnpm dev/test/build`、“怎么加功能域”？」
   有 → 移到项目 `README.md` / `docs/`。
3. 「文中引用的路径 / 仓库，客户机器上存在吗？」
   不存在 → 删掉引用，改写成自包含表述。
4. 「文件名是 A01 / B01 / C01 形式吗？已经登记进 `SKILL.md` 路由表了吗？」
   没有 → 按第四节改名并登记。
5. 「这条讲的是‘怎么用’，还是‘怎么开发’？」
   是开发 → 不属于 assert-skill。

## 七、一个项目可打包多个 skill（多 skill 模型）

`assets/` 下**不止一个** skill 是常态：项目主 skill（= `package.json.name`，默认 install）
+ 若干配套 skill（如实时任务接力）。多个 skill 由 `assets/groups.json` 聚合，`--group`
一键装一组。完整命令面与约定见 [[B04-multi-skill]]；assert 阶段至少核对：

- [ ] `assets/<package.json.name>/SKILL.md` 存在（默认 `skill install` 装的就是它）
- [ ] `groups.json` 默认 group key = `package.json.name`；每个 `skills[i]` 对应真实存在的
      `assets/<name>/SKILL.md`
- [ ] `skill list` 列出全部可装 skill 并标出默认项；`skill groups` 列出 group → 其 skill
- [ ] `skill install <name>`、`skill install --group=<key>`、`skill get [name] [--group]`
      三态都能跑通；`<name>` 与 `--group` 互斥、未知 group 报错并列出可用项
- [ ] 删掉 `groups.json` 仍可用（降级为目录扫描），不崩

> 多个 skill 各自只回答「这个 skill 怎么用」；它们之间的关系（哪个默认、哪组同装）由
> `groups.json` 承载，**不要**在每个 SKILL.md 里重复罗列其他 skill 的内容。

## 八、为什么这个顺序不能颠倒

| 顺序 | 后果 |
| --- | --- |
| ✅ 先 skill 后代码 | skill 写出来的就是「项目想被怎么用」，代码去匹配契约 |
| ❌ 先代码后 skill | skill 变成「给现有代码补使用说明」——必然遗漏反向 case，且随代码漂移 |

第一条命中的，是这条原则的**最强反模式**：写完代码再来补 skill，缺什么补什么，没人会主动暴露“我设计错了”的地方——因为代码已经按错的设计跑起来了。skill 沦为文档副作用，而不是契约源。

## 九、SKILL.md 的触发词怎么写（自检）

写完 SKILL.md 的 `description` 字段后，对照下面 4 条自检，**任一不达标就别提交**：

- [ ] 用「当用户……时使用」开头（症状描述，非流程描述）
- [ ] 5-10 个触发词（命令动词、主题词、典型场景）
- [ ] 明确写了 1-2 个「不适用」的反例
- [ ] `name` 是小写连字符（`<项目>-<角色>` 形态），不带版本号

> 反例：`description: 总结成 skill` —— 这不是触发词，是 skill-creator 的触发词，且没有症状也没有反例。

## 十、与 key_board 的协作

- 写 `assets/` 内容前，先过 key_board 的 [[X04-产物作用域]]：assert-skill 是**随包分发的项目级 skill**——命令与数据路径用真实值，但不得带入作者机器上的源码、仓库或来源；整个 skill 必须自包含。
- 创建新 skill 时走 key_board 的 `references/Z01-创建新skill.md`；ref 命名与序列划分走 `references/X02-ref路由优化.md`。
- **不要**把 key_board 的方法论搬进 assets：客户侧 agent 只需要 usage，不需要 skill 生命周期的知识。

## 十一、错误案例

| 错误操作 | 实际后果 | 正确做法 |
| --- | --- | --- |
| 项目初始化只写 `bin/` 和 `package.json`，skill 留到发版前补 | agent 在发版前不会用这个项目——所有“脚手架效果”打折到 0；补的时候容易写错触发词 | 阶段 1 就把 `assets/<skill>/SKILL.md` 交付 |
| 把 `00-设计思想.md` / 架构 / 分层 / lint 写进 assets | 客户没有源码和开发环境，这段知识对他永远是噪音；真正需要它的仓库开发者反倒在项目里找不到 | 设计文档归项目 `docs/`；assets 只放 A/B/C 用法 ref |
| 用裸 `00-`、`01-`、`NN-` 给 ref 编号 | 编号不承载序列信息，和 key_board 的标准序列规范脱节 | 用 `A01` / `A02` / `B01` / `C01`，并登记进 `SKILL.md` 路由表 |
| 触发词只写命令动词（“serve / install”） | agent 接到“帮我建个本机工具”这种自然语言时识别不到 | 触发词至少含 1 个**主题词**（“管理面板 / 脚手架 / 本机工具”） |
| 一个项目一个 skill，但反过来所有项目共用一个 skill | agent 分不清“这个项目是干什么的”和“这个脚手架是干什么的”——前者项目级，后者骨架级 | 骨架级 skill 与项目级 skill 分开；项目级 skill 在项目自己的 `assets/<skill>/` 下 |
| 把「改这个项目本身」（加功能域要碰哪几处、lint 怎么改）写进 `assets/<skill>/` | 用户侧 agent 手上没有 `src/`，这段知识对它永远用不上；而真正需要它的人（仓库开发者）在项目仓库里找不到 | assets 只回答「**怎么用**」；开发规范归位到项目 `README.md` / 脚手架 skill |
| 在 assets skill 里写开发参考出处（「结构参照 xx 源码路径」）或项目本地目录约定 | assets 是全局安装的 skill：用户机器上没有那些仓库、那个项目里没有那些目录，引用全是死链 | 参照研究开发期完成并消化成自包含原则；涉及「写到哪」一律写「当前项目的文档目录（如 `docs/`）」 |
| skill 写完不跑 `skill-creator` 的触发词评估 | 写的时候自我感觉良好，实际触发率 10% | 写完跑一次评估，按数据调描述 |

### [2026-10-11] key_board 操作教训

> 本 ref 是全局 skill：操作教训只记**通用模式**，不落具体项目名/项目路径——具体案例细节归项目仓库与操作者自己的记录。

| 错误操作 | 实际后果 | 正确做法 |
| --- | --- | --- |
| 给某 skill 写新 ref 时，把参照研究的来源（外部项目源码路径）写成正文引用，还做了「参照实现」对照表 | 用户装的全局 skill 里全是死链引用——用户机器上没有这些仓库；知识被包装成「文献综述」而非可执行要领，被用户指出后才删除改写 | 参照研究是开发期动作：研究完成后只把消化的原则写进 assets，出处留在项目仓库的开发文档/提交说明里 |
| 扫描时把某 ref 里的 `.claude/repo/_self/`、某插件的项目内 specs 路径判为「用户自己生态的约定，不算违规」 | 被用户纠正：assets 全是全局 skill，项目文档级目录约定同样不能进——「如…或…」的软化措辞不改变引用了特定项目路径的事实 | 判据只有一条：这个路径在**任意机器的任意项目**里都存在吗？不存在就改写成「当前项目的文档目录（如 `docs/`，项目已有约定就用现有的）」 |
| 本 ref 早已写明 assets 判据，实际写 assets 时依然违规 | 规范存在 ≠ 被执行；写的时候凭「刚研究完、出处很自然要带上」的惯性落笔 | 写 assets 每写完一个 ref，当场跑「两个自检问题」；把自检做成写完后的固定动作，而不是靠事后回忆规范 |
| 把含具体项目名/项目案例的操作教训原样记进全局 ref | 全局 skill 被塞进项目级细节，在其他项目加载时成为噪音，违反本 ref 自己的判据 | 教训先 genericize（项目名 → 「某项目/某 skill」，路径 → 通用形态）再入全局 ref；具体案例留在项目仓库或操作者本地记录 |

### [2026-10-25] assert-skill 的读者边界与序列命名

| 错误操作 | 实际后果 | 正确做法 |
| --- | --- | --- |
| 把 `00-设计思想.md` 当作 assets 的必交付，和 `SKILL.md` 一起下沉 | 客户装包后没有源码、开发环境和构建链，架构/分层文档对他不可执行；assets 变成开发手册，真正该看的是项目仓库 | 设计文档归项目 `docs/` 或 `README.md`；assets 只交付 `SKILL.md` + A/B/C 用法 ref |
| 用裸 `00-` / `01-` / `NN-` 命名 ref | 与 key_board 的标准序列规范脱节，读者无法从文件名判断“属于哪类使用路径” | 统一 `<序列字母><两位序号>-<主题>.md`：A01 / A02 / B01 / C01，并在 `SKILL.md` 路由表登记 |
| 只强调 assets 是“用户侧”，却没写清用户**没有开发环境** | 写作者仍会把源码结构、lint、加功能步骤当成“用户会需要”的知识带进 assets | 在 ref 开头直接声明读者画像：只有 CLI/面板/数据，没有源码/构建链/开发环境，只讲怎么用 |
