# 04 · Skill 创建的前期架构考虑

> 归属主文档 [[server-cli-web-scaffold]]。**写代码前先写 skill；写完 skill 再写代码。**
>
> 这一节插在 `[[01-bootstrap-serve-first]]`（定骨架）之后、`[[05-state-storage]]`（接状态）之前——因为它要回答的是"你这个项目到底要被谁调用、怎么被调用"，决定所有后续 action 的形态。

## 一句话原则

**skill 不是文档，是产品的一部分。** 项目初始化 = `SKILL.md` + `references/` 一个思想文档同时落地。两者皆缺，等于把这个项目对 agent 设为不可用。

| 时刻 | 该交付什么 | 缺了会怎样 |
| --- | --- | --- |
| 阶段 1 写完骨架 | `SKILL.md` + `references/00-设计思想.md`（或等价骨架级文档） | agent 拿到这个项目不知道它是干啥的，触发词写不出 |
| 每个新功能域首次落地 | 该域对应的 `references/<域>.md`（场景级 SOP） | agent 能跑命令但不知道怎么用、用错了没人救 |
| 状态/存储/发版契约稳定时 | 对应 `references/<编号>-<主题>.md` | 同上，只是触发频率更低 |

> **"思想文档"是骨架级**——讲架构、边界、不变量、路由原则。任何"什么时候读它"由主文档的路由表决定，不由 agent 自由发挥。

## 思想文档的最小骨架（初始化即写）

新建一个项目时，**`SKILL.md` 和 `references/` 必须同时存在**。下面这个骨架不是装饰，是为了让 agent 在第一次接触项目时不靠猜：

### SKILL.md 必含

- **触发词清单**（一句话能描述 + 关键词 5-10 个）
- **核心不变量**（3 条以内，每条用 1-2 个例子说明"违反会怎样"）
- **核心命令/动作表**（短表，链接到 references 详读）
- **什么时候不用**（反例，避免误触发）

### references/00-思想文档 必含

按本 skill 的编号约定命名为 `00-<主题>.md` 或 `00-设计思想.md`。必含五段：

1. **驱动关系图**（一张 ASCII / Mermaid，说明谁依赖谁）
2. **分层与依赖方向**（哪一层只能依赖哪一层；为什么）
3. **关键不变量**（每条配 1 个"违反会怎样"的真实场景）
4. **失败 vs 业务结果**（沿用主文档第 3 条不变量的二分法）
5. **错误案例表**（3-5 条"踩过的坑"，每条给正确做法）

> **不要在这个文档里放场景级 SOP**——例如「怎么调 `xxx serve`」「参数怎么传」都该进独立的场景 ref。00 思想文档回答"为什么这么设计"，场景 ref 回答"怎么用"。

### 场景级 ref 按需扩展

每个功能域、每个稳定下来的工程契约，对应一个独立 ref，编号按本 skill 的 `NN-<主题>.md` 约定：

- `02-web-panel`（视觉规范）/ `03-cli-surface`（对外契约）/ `05-state-storage`（存储约定）—— 这些是**本骨架的默认场景**，不是这个 skill 创建的项目该有的。
- 一个具体项目会有自己的 `references/<域>.md`，描述该域的命令、参数、典型坑。
- **扩展原则**：先看是否已有 ref 可加节，没有再新建 ref——与 key_board 的「路由优先级」一致。

## 为什么这个顺序不能颠倒

| 顺序 | 后果 |
| --- | --- |
| ✅ 先 skill 后代码 | skill 写出来的就是「项目想被怎么用」，代码去匹配契约 |
| ❌ 先代码后 skill | skill 变成「给现有代码补使用说明」——必然遗漏反向 case，且随代码漂移 |

第一条命中的，是这条原则的**最强反模式**：写完代码再来补 skill，缺什么补什么，没人会主动暴露"我设计错了"的地方——因为代码已经按错的设计跑起来了。skill 沦为文档副作用，而不是契约源。

## SKILL.md 的触发词怎么写（自检）

写完 SKILL.md 的 `description` 字段后，对照下面 4 条自检，**任一不达标就别提交**：

- [ ] 用「当用户……时使用」开头（症状描述，非流程描述）
- [ ] 5-10 个触发词（命令动词、主题词、典型场景）
- [ ] 明确写了 1-2 个「不适用」的反例
- [ ] `name` 是小写连字符（`<项目>-<角色>` 形态），不带版本号

> 反例：`description: 总结成 skill` —— 这不是触发词，是 skill-creator 的触发词，且没有症状也没有反例。

## 与 key_board 的协作

如果你这个项目本身是个"工具生成器"或"skill 分发器"，那么创建这个项目**前**应先用 [[key_board]] 走 `references/创建新skill.md` 的 SOP；创建这个项目**时**再按本 ref 的最小骨架落地 skill。这样 skill 既符合 key_board 的元规范，又符合本骨架的工程契约。

## 错误案例

| 错误操作 | 实际后果 | 正确做法 |
| --- | --- | --- |
| 项目初始化只写 `bin/` 和 `package.json`，skill 留到发版前补 | agent 在发版前不会用这个项目——所有"脚手架效果"打折到 0；补的时候容易写错触发词 | 阶段 1 就把 `SKILL.md` + `references/00-思想文档.md` 一起交付 |
| 思想文档里塞场景级 SOP（"怎么调 serve"） | 思想文档变长；场景级内容散落多地，按主题找找不到 | 思想文档只讲"为什么"；场景进独立 ref；路由表统一索引 |
| 触发词只写命令动词（"serve / install"） | agent 接到"帮我建个本机工具"这种自然语言时识别不到 | 触发词至少含 1 个**主题词**（"管理面板 / 脚手架 / 本机工具"） |
| 一个项目一个 skill，但反过来所有项目共用一个 skill | agent 分不清"这个项目是干什么的"和"这个脚手架是干什么的"——前者项目级，后者骨架级 | 骨架级 skill 与项目级 skill 分开；项目级 skill 在项目自己的 `assets/<skill>/` 下 |
| skill 写完不跑 `skill-creator` 的触发词评估 | 写的时候自我感觉良好，实际触发率 10% | 写完跑一次评估，按数据调描述 |
