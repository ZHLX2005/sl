# X01 — ref 体系 SOP

> 一条主线：**SKILL.md 只作 ref-map，场景内容全在 `references/`，ref 一律序列命名、只写 SOP、随场景即时增补。**

## 0. 强制标准（所有 skill 一律如此）

1. **单 SKILL.md 作 ref-map**：只放 原则 / 路由表 / 序列总览 / 检查清单；场景内容全在 `references/`；不另起根级 README / 指南 / INDEX。**不论落在哪个平台目录（`.claude/` / `.agent/` / `.workbuddy/`…）、项目自带的静态 skill 资源目录，还是面向开发者还是终端用户，架构一律相同。**
2. **references/ 全部序列命名**：`<序列字母><两位序号>-<名称>.md`，从第一篇起就编号，无数量门槛 → §1。
3. **ref 只写 SOP**：步骤 / 判定 / 正反例。不写背景知识、百科、术语科普、经验流水账。
4. **场景一到就建 ref**：新场景当场建——能补进既有 ref 就补，主题独立才新建。主文档不随场景变多而变厚。
5. **写内容前过作用域闸** → [[X02-产物作用域]]（通用级零项目上下文 / 项目级写真实路径）。

## 1. 序列规则

> 命名与归类是**默认动作**，不需要用户触发：建 ref、拆 ref、合并 skill 时一律套用。

### 1.1 编号规则

格式：`<序列字母><两位序号>-<名称>.md`

```
A01-xxx.md      ← A 序列第 1 篇
A02-xxx.md
B01-xxx.md      ← B 序列第 1 篇
```

| 组成 | 规则 |
| --- | --- |
| 序列字母 | 大写，一个字母 = 一个动作类别 |
| 序号 | 两位，从 `01` 起递增；`00` 保留给序列元数据 ref |
| 名称 | 保留语义名、连字符连接——`A01-沉淀为ref.md` 而非 `A01.md`（文件名要能一眼读懂） |

- 编号从第一篇起就有，**不设门槛**；序列号承担分类信息，不是流水号。
- `00` 元数据 ref：仅当某序列成员多、边界容易混时才建（作为该序列入口），**不承载动作 SOP**；单成员序列直接从 `01` 起，不造空壳。普通业务 skill 不需要 `A00`——SKILL.md 自己就是总览。
- 字母占用：业务 skill 用 A/B/C…；key-board 自己用 X/Y/M，互不撞名。

### 1.2 序列划分

- 按**读者 / 动作类别**划分；不按主题词、不按文件名字母序、不按创建时间。
- 判据：读这些 ref 的人，会不会因为场景不同而只读其中一个序列？**是 → 分序列；否 → 同序列。**
- 每序列内 `01` 给最高频 / 主流程的 ref，后续按流程顺序递增。
- 顶层序列数控制在 **2-4 个**（超过说明分类维度太细，读者记不住字母）。

### 1.3 子序列（默认不用）

格式：`<序列字母><子序列字母><两位序号>-<名称>.md`（`Aa01` / `Ab01`）。

启用条件（**同时**满足才开）：

1. 该序列动作 ref > 8 个（读者一屏扫不完）；
2. 且出现 ≥2 个清晰的二级动作类别，同类别成员共享读者路径；
3. 且顶层序列数仍 ≤4 个。

- 子序列不设 `00`；自成一类动作的部分**升级为新的顶层序列**（如 `D`），不塞成 `Ab`。
- 按序列独立判断：只有膨胀的那个序列开子序列，其他序列保持顶层平铺。
- 子序列字母只增不复用；成员撤并后在同子序列内收拢重排。

### 1.4 主文档结构：序列总览先于明细

**序列总览必须排在 ref-map 明细表之前**——读者先建立"字母 = 类别"的映射，再读逐行明细。

```markdown
## 序列总览（先读这里）

| 代号 | 类别 | 成员 |
| --- | --- | --- |
| A | 结构演化与维护 | [[A00-结构演化路由]]（入口）→ A01 / A02 |
| B | 合并 | [[B00-合并路由]]（入口）→ B01 / B02 |

## 场景路由（ref-map 明细）

| 场景 | 信号 | 何时读取 | 代号 | 路径 |
| --- | --- | --- | --- | --- |
| ... | ... | ... | ... | ... |
```

- 明细表每行的「代号」列与总览表对应；读者只需记住"进 A 序列先看 A00"。
- **只加一表一列，不新增场景级章节**——主文档行数不因序列化增长。

### 1.5 给存量 skill 补编号

> 适用对象：本标准之前建的、ref 还是平铺命名的 skill。新建 skill 从第一篇起就按 §1.1 命名，不走这套改造。

**Step 1 盘点与划分**

1. 列出 `references/` 全部 ref 及各自职责；
2. 按动作类别归组，产出划分表（字母 → 类别名 → 成员）；
3. 序列数 2-4 个；逐序列判断是否需要 `X00` 入口、是否需要子序列。

**Step 2 重命名**

```bash
git mv references/<原名>.md references/<代号>-<原名>.md
```

用 `git mv` 保历史；同批全部重命名，不留半编号半平铺的混合态。

**Step 3 全量修正 [[链接]]**

范围：主 SKILL.md（序列总览、ref-map、路由优先级、易错表、正文锚点）+ 所有 ref 内部互引 + 仓库内其他 skill 的跨 skill 引用。改完 Grep 旧名确认零残留。

**Step 4 主文档加「序列总览」+ ref-map 加「代号」列**（按 §1.4 模板）。

**Step 5 校验**

- [ ] 动作 ref 全部 `01` 起编号；`00` 只给序列元数据 ref，且不含动作 SOP、无空 ref
- [ ] 序列数 2-4 个，每序列有明确类别名
- [ ] 子序列未膨胀就不开；自成一类的部分升级为顶层序列
- [ ] 序列总览在明细表之前
- [ ] `[[旧名]]` 链接零残留（含跨 skill 引用）
- [ ] 主文档未新增场景级章节；核心流程 / 触发条件未变

### 1.6 续号与收拢

- 新 ref 属于已有类别 → 沿用该序列字母，取 max 序号 +1。
- 新 ref 属于某子类别 → 取该子序列 max 序号 +1。
- 单序列成员持续增多但够不上新顶层类别 → 按 §1.3 开子序列。
- 新 ref 是全新类别 → 启用新字母（如 `D`），从 `D01` 起（`D00` 留给潜在入口）。
- **收拢（铁律）**：删除 / 合并某成员后，后续成员**自动收拢重排**（A03/A04 撤并后 → A02/A03），不留空洞跳号；用 `git mv` 保历史，并全量修正 `[[代号-原名]]` 链接，Grep 旧代号零残留才算完成。
- 整个序列清空时字母才废弃、不复用给新类别。
- 序列内成员边界频繁混淆 → 扩充 `X00` 的路由行，不是继续加成员。

## 2. 沉淀为 ref（建 / 拆 / 补 / 登记）

### 2.1 拆一个主题 → 新 ref

**Step 1 识别主题**

- 定位到具体章节（起止行号）；
- 主题能独立成立 = 有明确触发时机 + 独立价值；
- 常见可沉淀：错误案例库、格式规范、API 速查、评估方法论、子领域差异细节。
- 不沉淀：主流程 / 触发条件 / 成功标准检查清单（跟着主文档走）；背景原理 / 术语科普（没有操作动作，拆出来只是搬字）。

**Step 2 设计 ref 结构**

```markdown
---
name: <ref-name>
description: <一句话说清这个 ref 干什么、什么时候读>
---

# <Ref 标题>

## 加载时机
（主 SKILL.md 的哪一步 / 什么场景必须读它）

## 详细内容

## 关联引用
```

- description 写"什么时候读"，不写"内容总结"。
- 先看目标 skill 兄弟 ref 的真实结构：有的 skill 惯例**无 frontmatter**、直接 `# 代号 · 标题`。**目标 skill 惯例优先**，上表只是默认值。

**Step 3 迁移内容**

- 先过作用域闸（[[X02-产物作用域]]）：通用级 → 剥离项目名 / 绝对路径 / 来源句（来源里的经验抽象成可复用判据）；项目级 → 确认真实路径没被占位符替换。
- 整章复制，保持原结构；内部链接改成 `[[ref-name]]`；删掉过时、重复、对其它 ref 的反向引用。

**Step 4 主文档留锚点**

原章节位置保留标题，内容清空，只留一句原则总结 + 锚点：

```markdown
详见 [[<ref-name>]]。

> 📎 详细内容见 [[<ref-name>]]。何时读：<具体加载时机>
```

**Step 5 路由表登记**

主 SKILL.md 的 ref-map 补一行：`| 场景 | 信号 | 何时读取 | 代号 | 路径 |`。已有索引表就补一行，没有就新建（格式见 §1.4）。

> ⚠️ **下沉必须彻底**：ref 里放新内容、主文档还留一份旧步骤 = 两处维护、迟早不一致。主文档原位置只剩原则 + 锚点。

### 2.2 在现有 ref 里加一节（不新建文件）

- 触发："在现有 ref 里加一节 / 补一段"。
- 走 2.1 的 Step 3-5，跳过 Step 1-2；**ref 数量不变**。
- 补完核对：路由表该 ref 行的"何时读取"已覆盖新场景；补进去的是 SOP 步骤 / 判定，不是知识条目。

### 2.3 一次落多个场景

- 触发：用户一次提多个需求，或 AI 主动扫出多个可独立主题。
- 步骤：① 列 SKILL.md 全部章节 → ② 识别可独立主题 → ③ 每个主题建一篇 ref（按 §1.1 命名）→ ④ 迁移内容 + 留锚点 → ⑤ 路由表逐条登记。
- 不为了拆而拆；拆完做角色分离检查（主文档残留的场景级内容一律下沉）。

### 2.4 存量补登记（ref 没写加载时机）

- 触发：已有 `references/`，但 SKILL.md 没写何时读。
- 步骤：① 列出现有 ref → ② 主文档加 ref-map（无索引表就新建）→ ③ 正文里强依赖某 ref 的步骤旁也留 `[[锚点]]`。
- "何时读取"写触发时机，不写内容总结。**本场景不改正文内容，只加引导。**

### 2.5 统一一批 skill 的 ref 架构

- 触发：用户要求一批 skill 统一结构。
- 步骤：① 选结构最完善的 skill 作模板 → ② 把 ref 模式抽象成清单（锚点格式、索引表列、frontmatter 要求、加载引导写法、命名规则）→ ③ 逐个应用 2.1-2.5 + §1.5 → ④ 每完成一个做最小验证（主题不重复、锚点齐全、代号不撞名）。
- 统一时发现主文档里场景内容与路由混杂，**顺手下沉**（走 2.1）——目的是让所有 skill 达到"主文档 = 原则 + ref-map"，不是把混乱格式化成统一的混乱。
- 每完成一个 skill 报一次进度，不要批量做完才汇报。

### 2.6 第二层切分（何时再切一层）

只在主切分已决定、ref 树已存在、用户要求"再切一层"时用。**问题永远是"按什么维度再切"**：按角色（读者不同）/ 按场景（主流程 vs 特例）/ 按受众（怎么用 vs 怎么造）。

强信号（满足其一即可切）：读者明确分两类且没人同时读；两边前置知识差很大；一边的更新频率远高于另一边；用户能说出"我只需要 X 视角"；一边有独立的操作流程或判定标准。

不切：看起来对立但其实写同一段内容；交叉引用 > 50%；总长 < 500 行；刚拆过一次（先观察 3 个月）。

切完做三件事：① 新 ref 覆盖原内容 100%（不能丢）；② 读者路径测试（各给一个 ref，问"你能完成任务吗"）；③ 访问埋点（3 个月后看是否真分流，没分流就合回去）。

## 3. 内容同步

> **本节分两层，按产出物作用域分开用：**
>
> | 层 | 适用 | 干什么 |
> | --- | --- | --- |
> | **事实层（§3.1）** | **仅项目级 skill** | 把 skill 里写的路径 / 类名 / API 与真实代码对齐 |
> | **经验层（§3.2）** | 通用级 + 项目级都适用 | 把用完 skill 后的踩坑与新模式落成可复用判据 |
>
> **通用级 skill 不要跑事实层**：它不指向任何真实代码路径 / 类名 / API，没有可对照的真值——逐条 grep 会得到满屏"假引用"的噪声结论。通用级只需走 §3.2。
>
> 作用域判定见 [[X02-产物作用域]]：**项目级**（用了真实路径 / 类名 / 接口名）才跑 §3.1。

### 3.1 事实层（仅项目级 skill，5 步）

> 真实代码是唯一真相：skill 里每条路径 / 类名 / API 都必须在代码里找得到；代码变了，skill 必须跟上。
> 增量（功能开发完成，提交/PR/merge 前）与全量（重构后 / 定期巡检 / 用户报"找不到"）流程一致，只是对齐范围不同。

**Step 1 确定范围**

```bash
git diff --name-only HEAD~1        # 提交前最近一次
git diff --name-only origin/main   # 功能分支 vs 主干
git status                          # 未提交的工作区
```

改动类型 → 影响：新增文件（模块未提及）/ 删除或移动（旧路径变假引用）/ 重命名（旧类名失效）/ 签名或接口变化（示例失效）/ 路由或配置字段变化（接口表过期）/ 新增依赖（工具栈说明过期）/ 新增子主题（可能需要新建 ref，走 §2）。

**Step 2 定位受影响的 skill**

```bash
grep -rln "路径片段\|旧类名\|旧函数名" <skills目录>/
```

**Step 3 逐项验证引用真实性**

```bash
# 1. 文件路径引用
grep -oP '[\w/.\-]+\.[a-z]+' <skill文档路径> | while read f; do
  [ -f "$f" ] && echo "✅ $f" || echo "❌ $f"
done

# 2. 类 / 函数引用（按目标语言换关键字：class / def / fn / struct）
grep -rn "class UserModel\|def login" --include="*.py"

# 3. 相对 import：从源文件目录解析后验证
python -c "import os.path; print(os.path.normpath(os.path.join(os.path.dirname('path/to/source.py'), '../../some/module.py')))"
```

验证必须覆盖 `SKILL.md` **和所有 `references/*.md`**。

> ⚠️ **锚点检查分两步**：先解析文件，再查符号在不在该文件里。实现搬走但文档仍写 `old.ts#fn` → 文件存在、符号已不在，假引用漏网。搬实现 = 搬引用，跑 `git grep -n "旧文件\.ts#"` 全量扫。
>
> ⚠️ **裸文件名会淹没真问题**：`role.ts` / `sop.ts` 这类裸名在仓库根下不存在 → 满屏 ❌。按项目约定补全候选前缀（`src/` `scripts/` `test/`…）再判存在。

**Step 4 修复（按优先级）**

| 优先级 | 发现 | 处理 |
| --- | --- | --- |
| 🔴 P0 | 假引用（文件 / 类不存在） | 修正路径；目标已删除则删该节并全局替换旧名 |
| 🟡 P1 | 过时描述（接口已重构） | 更新描述、接口表、依赖矩阵 |
| 🟢 P2 | 遗漏新模块 / 新模式 | 补充；独立子主题新建 ref（走 §2） |

```bash
grep -rln "src/auth/login\.py" <skills目录>/ | xargs sed -i 's|src/auth/login\.py|src/auth/oauth.py|g'
```

替换后人工 review diff（防误伤同名 token），改完接口表手动跑一遍示例，frontmatter description 里提到的旧模块名一并更新。**已知假引用当场修，不放行。**

**Step 5 验证 + 提交**

```bash
for doc in <skills目录>/<skill>/SKILL.md <skills目录>/<skill>/references/*.md; do
  grep -oP '[\w/.\-]+\.[a-z]+' "$doc" | while read f; do
    [ -f "$f" ] && echo "✅ $f" || echo "❌ $f"
  done
done
```

增量模式：skill 同步与代码改动**同一 PR**（或紧随 `chore: sync skills` commit），PR 里标注同步了哪些 skill/ref。全量模式：输出审计报告（引用 | 状态 | 修复）留档。

**发版场景收尾**（"更新 skill + 发布次版本"必走）

1. 先改全再打 tag：代码 → skill（3.1）→ `package.json` version → `CHANGELOG.md` → 同一次提交 → `git tag vX.Y.Z`；
2. 确认改动进了提交：skill 目录常在 `.gitignore` 里但文件是 tracked 的，`git add -A` 会静默跳过（只提示 ignored）；提交后 `git status --short` 必须为空、`git diff --cached --stat` 里要有 skill 文件；
3. push 分支 + tag，用 `gh run watch <id> --exit-status` 等 CI / Release 都绿；
4. `npm view <pkg> version` 有 CDN 延迟，等 ~30s 复查，别据此判定发布失败或重发（同版本重发 403）。

skill 里的「数据快照：vX.Y.Z」跟着 bump，frontmatter `description` 补上新能力关键词。

### 3.2 经验层（用完 skill 后的反思沉淀）

适用：通用级 + 项目级都适用。

触发："把这个经验记到 skill 里" / "记一下这个坑"。**项目级 skill 先事实后经验**：功能开发后先走 3.1，再走本节，同批进 PR。

1. 回顾分类：skill 说对了吗？发现新模式了吗？踩坑了吗？缺什么关键步骤？
2. 转 good_eg / bad_eg：每条踩坑**先记 bad_eg（根因 + 修复代码），再加 good_eg（正确做法）**，两者齐了才算记完。
3. 归属：特化子主题 → 对应 ref；核心流程 → 主文档错误案例表；缺独立主题 → 新建 ref（走 §2）。
4. 验证：新加的引用 `test -f` / grep 确认存在；frontmatter 完整；`[[锚点]]` 有效。

> 经验必须落成**可复用的判据或 SOP 步骤**，落进既有 ref 的对应小节；只有独立成场景的经验才新建 ref。不建"经验堆"ref、不写流水账。

## 4. 创建新 skill

> 使用条件：主 SKILL.md 路由优先级确认「无现有 ref 可扩展」时才走本节。

### 4.1 产出物架构

```
<宿主目录>/<skill名>/
├── SKILL.md          ← 唯一入口，只作 ref-map：原则 + 路由表 + 序列总览 + 检查清单
└── references/       ← 场景级 SOP 全部在这里
    ├── A00-xxx.md
    └── A01-xxx.md
```

- `<宿主目录>` 由载体形态决定（[[X02-产物作用域]] Step 2）：平台 skill 目录（`.claude/skills/` / `.agent/skills/` / `.workbuddy/…`）、项目自带静态 skill 资源（`assets/skills/`、`<pkg>/skills/`）、用户级目录（`~/.claude/skills/`）。**开发级 / 面向开发者的 skill 与终端用户向 skill 一视同仁。**
- 只有一个根 SKILL.md，不建第二个根级 md。
- SKILL.md 零场景级内容——具体步骤、示例、判定细节、错误案例正文全在 ref。
- references/ 一律序列命名（§1.1），从第一篇起就编号。
- 通用级 / 项目级、对话来源 / 代码库来源、SOP 类 / 规范类——**架构一律相同**，差异只在内容怎么写（作用域）与场景怎么切。

**Step 0 声明作用域**（动手前第一件事）

| 作用域 | 内容写法 |
| --- | --- |
| 通用级（换个项目仍成立） | 不写项目名、绝对路径、人名、内部术语、来源句；举例用 `<占位符>` |
| 项目级（脱离本项目无意义） | 头部声明"仅适用于 <项目>"，路径 / 模块名写真实值 |

判定三连问见 [[X02-产物作用域]]。

### 4.2 依赖 skill 声明与校验

动手前在回复顶部**分两行**输出，两行成员互不重叠：

```
元层依赖(仅本次创建用，不写入任何文件): skill-creator, writing-skills
产物层依赖(将写入新 skill): <仅用户指名且属于新 skill 运行时的 skill；若无则写「无」>
```

- 判定归属：问"新 skill 每次运行时还需要它吗？" 否 → 元层（用完即弃、不落盘）；是 → 产物层（写进新 skill）。`skill-creator` / `writing-skills` 恒为元层。
- 逐个加载校验；**任一失败即终止**：

```
⛔ 依赖 skill 无法加载：<skill名>
已终止本次 skill 创建。请先安装/修复该依赖后重试。
```

示例：用户要"用 /k6 压测 + 按 /tool-isolation 建目录 + 报告含 commit hash" → 产物层 = `k6`、`tool-isolation`；元层 = `skill-creator`、`writing-skills`（**不**进新 skill）；校验四个都能加载，任一失败终止。

### 4.3 来源 A：对话 / 反思

触发："总结成 skill" / "保存对话为 skill" / "做成 skill"。

1. **依赖校验**（4.2）——失败即终止。
2. **反思**：复盘（`sc:reflect` 或手动）——成功案例与根因、错误案例与根因、坑点与预防。
3. **Capture Intent**：这个 skill 解决什么问题？什么时候触发？输出格式是什么？
4. **建目录**：`mkdir -p <宿主目录>/<skill名称>/`（宿主目录按载体形态定，见 [[X02-产物作用域]] Step 2）
5. **写 SKILL.md（ref-map）**：frontmatter（name / description）+ 路由表 + 序列总览 + 原则 + 检查清单。场景内容不写在这里。
6. **建 ref 树**：把场景拆成独立 ref，按 §1.1 命名（`A01-…` 起），路由表逐条登记"何时读取"。
7. **校验**：走 §5 清单。

**错误案例必须有**（放主文档错误案例表或对应 ref，二选一，不得省略）：

```markdown
| 错误操作 | 实际后果 | 正确做法 |
|---------|---------|---------|
| ... | ... | ... |
```

### 4.4 来源 B：真实代码库

触发："为这个项目创建模块规范" / "分析这个目录做成 skill" / "防止代码腐蚀"。

**Step 1 侦察**

```bash
find <target-dir> -type f \( -name "*.js" -o -name "*.py" -o -name "*.go" -o -name "*.rs" \) | sort
find <target-dir> -type f -name "*.java" -exec wc -l {} + | sort -rn | head -20
```

维度：文件数量（复杂度）/ 文件大小（> 300 行标记过大）/ 命名模式（模块划分）/ import 依赖图（职责边界）。

**Step 2 分析依赖**

```bash
grep -rn "^import\|^from.*import\|^use " <target-dir>/ --include="*.py" --include="*.rs" | sort
```

产出依赖矩阵（文件 | 导入模块 | 被引用次数 | 行数 | 状态），状态含"过大"等标注。

**Step 3 产出**：按 4.1 架构 → SKILL.md 作 ref-map，references/ 里放序列命名的 SOP ref（职责边界、检测方式、正反案例）。检测标准必须给具体命令，不写"代码要保持整洁"。**方法语言无关，产物项目级**（头部声明"仅适用于 <项目>"，路径写真实值）。
落点按载体定：仓库内平台目录（`<repo>/.claude/skills/<name>/`）或项目自带静态资源（`<pkg>/assets/skills/<name>/`）；选后者时整个 skill 必须**自包含**——不带作者机器上的源码、仓库、绝对路径与来源（见 [[X02-产物作用域]] Step 5）。

**Step 4 验证**

```bash
grep -oP '[\w/.\-]+\.[a-z]+' .claude/skills/<name>/SKILL.md | while read f; do
  [ -f "$f" ] && echo "✅ $f" || echo "❌ $f"
done
grep "class AClass\|struct AStruct" $(find . -name "*.py" -o -name "*.go")
```

验证覆盖 `references/*.md`。

**创建之后**：维护回到本 ref——代码改动后同步（3.1）、使用后经验沉淀（3.2）、ref 结构演化（§2 / §1）。可选调用 `skill-creator` 写触发测试用例。

## 5. 校验清单

**架构**

- [ ] 只有一个根 SKILL.md，且只作 ref-map（无场景级内容、无第二个根级 md）
- [ ] `references/` 全部为 `<序列字母><两位序号>-<名称>.md`
- [ ] 每个 ref 开头有「加载时机」；主文档路由表逐条登记"何时读取"
- [ ] 一 ref 一主题；ref 写的是 SOP 步骤 / 判定，不是知识条目
- [ ] 主文档原位置只剩原则 + `[[锚点]]`，无场景级内容残留
- [ ] 序列总览在 ref-map 明细之前；`[[旧名]]` 链接零残留（Grep 全仓，含跨 skill）
- [ ] 核心流程 / 触发条件未改

**事实**

- [ ] 引用的路径 / 类名 / 符号均已在代码中验证存在（覆盖 `references/*.md`）
- [ ] 已知假引用当场修复；增量同步与代码改动同一 PR

**横切**

- [ ] 产出物作用域已声明：通用级零项目上下文，项目级使用真实路径（见 [[X02-产物作用域]]）
