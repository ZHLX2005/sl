# X02 — 产物作用域与载体形态

> **使用条件**：任何"要往 skill 里写内容"的动作**动手前**——创建新 skill（[[X01-ref体系SOP]] §4）、把内容沉淀进 ref（[[X01-ref体系SOP]] §2）。
>
> 本 ref 只回答两个问题：**① 这份产出该带多少上下文？② 它落在哪？** 不判断内容对不对。

| 轴 | 判什么 | 影响 |
| --- | --- | --- |
| **内容作用域**（Step 1） | 通用级 / 项目级 | 上下文密度：零项目上下文 vs 写真实值 |
| **载体形态**（Step 2） | 落在哪种目录 | 落点路径 + 自包含要求 |

> **两轴正交**：载体不改变作用域判定，作用域不决定落哪；**两者都不改变架构标准**——不论落在哪、面向谁，都是单 SKILL.md 作 ref-map + 序列命名 refs + ref 只写 SOP（[[X01-ref体系SOP]] §0）。

## Step 1: 判内容作用域（三连问）

依次问，**任一为"是"即判为项目级**：

1. 内容里的名字（项目名 / 模块名 / 表名 / 接口名）**换掉一个**，这份 skill 还成立吗？→ 不成立 = 项目级
2. 别人（或别的仓库的 AI）拿到它，**不需要访问作者的环境**就能照着执行吗？→ 不能 = 项目级
3. 它的触发时机是否依赖某个**具体目录 / 仓库 / 服务**的存在？→ 依赖 = 项目级

| 作用域 | 一句话 | 典型例子 |
| --- | --- | --- |
| **通用级** | 换个项目 / 机器 / 同事，仍然成立 | `tool-isolation`、`cli-standard`、`key-board`，以及任何"方法论 / 流程 / 规范"型 skill |
| **项目级** | 脱离这个项目就没有意义 | 某仓库的模块规范、某私有服务的部署 SOP、随包分发的项目专属 skill |

> **按 ref 粒度判，不要一刀切**：一个 skill 里不同部分可能作用域不同。主文档是通用方法论、某个 ref 是某项目的具体配置——就在那个 ref 头部单独声明适用范围，不要为了"统一"把整包升格或降级。

## Step 2: 判载体形态（落在哪）

**默认落点是 `.claude/skills/<name>/`**——用户没特别说，就生成到 `.claude`。下表其余行都是**明确指定或天然如此**时才走。

| 载体 | 典型位置 | 什么时候用 | 特点 |
| --- | --- | --- | --- |
| **平台 skill 目录（默认）** | `.claude/skills/<name>/` | **默认**：用户没说别的就落这里 | 平台按约定路径发现并加载 |
| **其它平台 skill 目录** | `.agent/skills/<name>/`、`.workbuddy/...` | 用户点名该平台 | 各平台按自己的约定 |
| **项目自带静态 skill 资源** | `assets/skills/<name>/`、`<pkg>/skills/<name>/` | 随项目或包分发；安装 / 引用时再落到某个平台目录 |
| **用户级目录** | `~/.claude/skills/<name>/` | 跨项目全局可用 |

**载体相关的规则**

1. **载体不改变架构标准**：无论落在哪，都是单 SKILL.md 作 ref-map + 序列命名 refs + ref 只写 SOP。**项目自带的静态 skill 资源也是 skill**，同样按 X01 规则优化，不因为"它只是个资源目录"就不排 ref。
2. **载体不改变作用域判定**：放在平台目录里的也可能是项目级（写本仓库的真实路径）；放在项目 assets 里的通常就是项目级。
3. **受众级别不影响架构标准**：面向开发者的 skill（开发级 / 规范级 / 工具级）与面向终端用户的 skill 一视同仁——同样单 SKILL.md + 序列命名 refs + ref 只写 SOP，不因读者是开发者就豁免。
4. **默认 `.claude`，换载体要有理由**：用户没说就不换——生成到 `.claude/skills/<name>/`。只有用户点名了别的平台，或产物本就是随项目/包分发的静态资源时，才落到对应目录。
5. **不要把某个平台的路径写死进内容**：要跨平台分发时，SKILL.md 与 ref 里用相对路径或 `<平台目录>` 占位符；确属某平台专属的，再写明平台名。

## Step 3: 红线一 —— 通用级 = 零项目上下文

通用级 skill 里**禁止出现**：

| 类别 | 例子 | 改法 |
| --- | --- | --- |
| 项目 / 仓库 / 服务名 | `dev_ctr_hello`、`encryptkv`、内部代号 | 删掉，或抽象为"目标项目" |
| 绝对路径 | `<项目根>\src\api`、`<user-home>/proj` 这类示例也别照抄真机的盘符与家目录 | 改 `<项目根>/api`，并在首次出现处说明这是占位符 |
| 人名 / 工号 / 客户名 | 真实姓名 | 删除或泛化 |
| 内部术语 / 黑话 | 只在某个团队内部流通的说法 | 换成通行表述 |
| 一次性时间锚点 | "上周那次事故"、"2026-10-08 的变更" | 抽成判据，去掉时间 |
| **来源句** | "参考 XX 项目的经验"、"按 nx-kv 的方式"、"从某内部文档抄的" | 见下 |

**来源句必须剥掉**：作者写来源觉得"有出处更可信"，但读者没有那个上下文——来源对读者不是证据，是死链接。把来源里**可复用的判据**抽出来，来源本身删除。

```
❌ 参考 XX 项目的经验，提交前要跑 lint
✅ 提交前必须跑 lint（否则 CI 会红）      ← 判据留下，出处无关
```

**允许出现的"具体值"**：`package.json`、`.gitignore`、`npm link`、`/usr/bin`、HTTP 状态码——判据一句：**这个具体值是不是"只有在作者的环境里才成立"**。

## Step 4: 红线二 —— 项目级 = 用当前项目的信息来写

**只有项目级 skill 才允许、且必须使用当前项目的信息**（项目名 / 仓库根 / 真实路径 / 模块名 / 内部约定的名称）。它的目标就是**在这个项目里可执行**，上下文不是污染，是必需品。

> **反向对照**：通用级 skill **一律不使用当前项目的信息**——一旦出现项目名 / 绝对路径 / 内部术语 / 来源句，就说明作用域判错了，回 Step 3 处理。

1. **头部声明适用范围**：`> 本 skill 仅适用于 <项目名>（<仓库根>）。` —— 防止传播后被误用到别的项目
2. **路径 / 模块名写真实值**：占位符在这里等于没写。能写绝对路径就写绝对路径；用仓库内相对路径时必须交代"相对谁是根"
3. **必要的环境信息写全**：技术栈与版本、内部约定的名称——因为读者没有这个项目的记忆
4. **不要为了"看起来通用"而抽象**：把真实路径换成 `<模块名>` 不会让 skill 更通用，只会让它不可执行

## Step 5: 载体相关的红线

| 载体 | 红线 |
| --- | --- |
| **项目自带静态 skill 资源 / 随包分发** | **必须自包含**：读者手上只有这一个目录，没有作者的环境。命令与数据路径写真实值，但**不得带入作者机器上的源码、仓库、绝对路径、内部来源**，也不得依赖未声明的产物层 skill |
| **平台 skill 目录** | 路径按平台约定；跨平台分发时不写死 `.claude/` 等具体平台目录；用相对路径或 `<平台目录>` 占位符 |
| **用户级目录** | 跨项目全局可见 → 基本只能是通用级；出现项目上下文就是错配 |

## 一句话判据

> **作用域声明决定上下文密度，载体决定落点与自包含要求。**
> 出现「局部项目概念或来源」却又是通用 skill → 作用域错配。
> 出现「作者机器的路径 / 仓库 / 未声明依赖」却又要随包分发 → 载体错配。

## 组合示例

| 内容作用域 | 载体 | 上下文怎么写 | 落哪 |
| --- | --- | --- | --- |
| 通用级 | 平台目录 | 零项目上下文 + `<占位符>` | `.claude/skills/<name>/` |
| 通用级 | 用户目录 | 同上 | `~/.claude/skills/<name>/` |
| 项目级 | 仓库内平台目录 | 真实路径 + 头部声明适用范围 | `<repo>/.claude/skills/<name>/` |
| 项目级 | 项目自带静态资源（随包分发） | 真实路径 + 自包含（不带作者机器路径 / 仓库 / 来源） | `<pkg>/assets/skills/<name>/` |

## 反例（来自真实产出）

| 现象 | 错在哪 | 改法 |
| --- | --- | --- |
| 通用 skill 里写 `D:\a_go\proj_1\dev_ctr_hello\api` | 绝对路径绑死作者的机器 | 改 `<项目根>/api`，并声明是占位符 |
| 通用 skill 里写"用法同 nx-kv" | 依赖读者环境里恰好装了另一个 skill | 内联成自包含描述，或声明为**产物层依赖**（见 [[X01-ref体系SOP]] §4.2） |
| 通用 skill 里写"这是给 encryptkv 做的" | 来源对读者无用 | 删除来源句 |
| 项目级 skill 写 `<模块目录>/handler.go` | 占位符让 skill 无法执行 | 写真实路径 |
| 项目级 skill 未声明适用范围 | 被误用到其他项目 | 头部加"仅适用于 X" |
| 随包分发的 skill 里写了作者机器的源码路径 / 仓库名 | 读者环境里全成死链 | 改成包内相对路径 + 删来源句，整体自包含 |
| 项目自带 assets 里的 skill 不排 ref、SKILL.md 写满内容 | 架构与其它 skill 不一致，改一处漏三处 | 按 [[X01-ref体系SOP]] §0 统一：单 SKILL.md + 序列命名 refs |

## 检查清单

**作用域**

- [ ] 已判内容作用域（三连问答得上），并在产出中体现
- [ ] 通用级：无项目 / 仓库 / 服务名，无绝对路径，无人名，无内部术语，无一次性时间锚点
- [ ] 通用级：无来源句；原有来源里的经验已抽象为可复用判据；占位符统一且首次出现处有说明
- [ ] 项目级：头部有"仅适用于 X"的适用范围声明；关键路径 / 模块名是真实值
- [ ] 逐句过了"换个项目 / 换台机器，这句还成立吗"

**载体**

- [ ] 已判载体形态，落点符合该载体约定
- [ ] 架构与 [[X01-ref体系SOP]] §0 一致（单 SKILL.md + 序列命名 refs + ref 只写 SOP），不论载体
- [ ] 随包分发：自包含——无作者机器路径 / 仓库名 / 来源句 / 未声明依赖
- [ ] 跨平台：不写死 `.claude/` 等单个平台目录

## 边界

| 不做 | 做 |
| --- | --- |
| ❌ 不判"内容对不对" | ✅ 只判上下文密度、作用域匹配、载体落点与自包含 |
| ❌ 不禁止通用 skill 举例子 | ✅ 例子要自包含，不引用读者拿不到的东西 |
| ❌ 不把项目级 skill 硬改通用 | ✅ 项目级就明写上下文 + 声明适用范围 |
| ❌ 不管载体把架构标准打折 | ✅ 放哪都按 X01 规则优化 |
