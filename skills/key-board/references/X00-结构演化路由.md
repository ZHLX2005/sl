# X00 — X 序列元数据：结构演化路由

> **本文件不承载任何动作 SOP**，只回答一个问题：**这个信号该进 X 序列的哪个成员？** 成员的执行细节一律看对应 ref。

## 成员分工边界

| 维度 | X01（结构 + 命名 + 内容 + 创建） | X02（作用域判定） |
| --- | --- | --- |
| 改什么 | ref 的数量、命名与序列代号、登记引导、架构统一、内容真实性、新 skill 产出 | 只判"上下文密度 + 作用域匹配 + 载体落点与自包含" |
| 触发 | 拆出去 / 补引导 / 统一架构 / 重编号 / 代码改动 / 定期巡检 / 用后有感悟 / 总结成 skill | 任何**要写内容**的动作动手前 |
| 依赖 | — | X01 写内容时被 §4.1 / §2.1 Step 3 触发；只判不写。载体判定结果决定 §4 的建目录路径与内容写法 |

> **X02 不参与上表分工**——它是**横切红线**，不存在"改什么"的维度，而是在 X01 动手写内容**之前**统一触发，判定产出物作用域（通用级零项目上下文 / 项目级使用当前项目的信息）。详见 [[X02-产物作用域]]。

## 序列内升级路径

- X01 §2.5（统一架构）发现场景内容混在主文档 → **顺手下沉**（走 §2.1）
- X01 §2 建 / 拆 ref 时 → 一律按 §1.1 命名（编号是默认动作）
- X01 §3 修复中发现文档结构问题（混场景、无路由）→ 转交 §2（存量补登记）
- X01 §4 创建新 skill 时定架构 → 直接按 §4.1（单 SKILL.md 作 ref-map + 序列命名 refs）落地
- 任一成员执行完 → 回主文档路由表登记"何时读取"；发现本表未覆盖的边界信号 → 把新行补进本文件（元数据 ref 的职责就是持续收敛序列内路由）
