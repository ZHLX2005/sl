# 场景 A / B / D：结构优化三场景

> 三个低频场景共用本 ref（触发频率均 ⭐⭐ 以下）。触发最频繁的场景 C 有独立 ref：[[场景C-沉淀为ref]]。

| 场景 | 频率 | 信号 |
| --- | --- | --- |
| A：SKILL.md 主题混乱 | ⭐⭐ | 多个子主题挤在一起，用户说"太大了/膨胀了" |
| B：添加 ref 加载引导 | ⭐ | 已有 references/ 但没写加载时机 |
| D：多 skill 统一 ref 架构 | ⭐ | 用户要求一批 skill 统一结构 |

## 场景 A：SKILL.md 主题混乱

**信号**：多个子主题挤在一起（通常是用户说"这个 skill 太大了"）。

1. 列出 SKILL.md 全部章节，识别可独立主题
2. 为每个主题创建 `references/<ref-name>.md`
3. 内容迁移 + 留 `[[ref-name]]` 锚点
4. 按主题自然分配，不为了拆而拆

**与场景 C 的关系**：A 是"AI 主动发现多个主题要拆"，C 是"用户点名一个主题要拆"。A 的每个主题的迁移动作，实际都走 [[场景C-沉淀为ref]] 的 Step 1-5；A 只是多了"先识别有哪些主题"这一步。

**主题识别判据**（同主 SKILL.md Step 2）：不是"内容多少"，而是"读这些章节的人，会不会因为场景不同而只读其中一部分"。是 → 拆；否 → 不拆。

**拆完后必须做角色分离检查**：主文档残留的场景级内容（步骤/示例/判定细节）一律下沉，主文档每章只留原则或路由。

## 场景 B：添加 ref 加载引导

**信号**：已有 `references/` 但 SKILL.md 没写加载时机——ref 存在但 AI 不知道什么时候读。

1. 列出现有 ref 文档
2. 在 SKILL.md 末尾加"何时读每个 ref"的引导段（索引表）
3. 用表格：`| ref | 何时读取 | 路径 |`

**引导段模板**：

```markdown
## 引用索引（按需加载）

| ref | 何时读取 | 路径 |
| --- | --- | --- |
| [[<ref-name>]] | [一句话加载时机，如"执行 xx 步骤时"] | references/<ref-name>.md |
```

**注意**：

- "何时读取"写**触发时机**（什么时候读），不写内容总结
- 如果正文流程中某一步强依赖某 ref，在那一步旁边也留 `[[锚点]]`，不要只在末尾索引表里出现
- B 场景不改正文内容，只加引导

## 场景 D：多 skill 统一 ref 架构

**信号**：用户要求一批 skill 统一结构（"统一所有 skill 的 ref 架构"）。

1. 选结构最完善的 skill 作模板
2. 把 ref 模式抽象成清单（锚点格式、索引表列、frontmatter 要求、加载引导写法）
3. 逐个 skill 应用
4. 每完成一个做最小验证（主题不重复、锚点齐全）

**统一时的角色分离红线**：统一过程中发现某 skill 主文档里场景内容和路由混杂，**顺手下沉**——统一架构的目的正是让所有 skill 都达到"主文档 = 原则 + ref-map"的终态，而不是把混乱格式化成统一的混乱。

**批处理注意**：每完成一个 skill 报告一次进度；不要批量做完才汇报（用户可能要中途调整模板）。

## 三场景共同的校验

- [ ] 主文档无场景级内容残留（每章要么是原则、要么是路由）
- [ ] 每个 ref 在 SKILL.md 有 `[[锚点]]` + 索引表登记
- [ ] 每条索引写的是"何时读取"而非内容总结
- [ ] 前置 skill（key_board / key_board_2）未受影响
- [ ] 核心流程/触发条件未变
