# Reference 分层判断 — 场景 C 的次级案例

> **本 ref 不常驻读取。** 它是 [[场景C-沉淀为ref]] 的**次级案例**：
> 当主切分
>

## 一句话原则

**已经决定"按主题拆 ref"之后，第二层问题永远是"按什么维度再切"。**
本 ref 帮你系统化这个第二层判断，避免凭直觉乱拆。

## 三种常见的分层维度

| 维度                  | 适用场景                                                    | 例子                                                                                           |
| --------------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| **按角色**      | 同一 skill 文档既被"底座开发者"也被"插件作者"读，但诉求不同 | `core-developer/`（基座/源码/扩展）vs `plugin-developer/`（插件契约/scaffold/walkthrough） |
| **按场景**      | 一个 ref 覆盖了"主流程 + 多个特例"，特例需要单独深入        | `场景C-沉淀为ref.md`（主）vs `references-Diversion.md`（次级：分层的判断方法论）           |
| **按受众/介质** | 同一主题对"读者"和"写者"诉求不同                            | "如何使用（consumer 视角）" vs "如何构建（author 视角）"                                       |

> **维度选错了的代价**：分错了之后**读者找不到**——比"不切"还糟。
> 所以第二层切分必须用**读者路径**来验证，而不是按主题相似度。

## 何时切第二层（强信号）

| 强信号                                           | 弱信号（先别切）                       |
| ------------------------------------------------ | -------------------------------------- |
| 读者明确分两类人，**没人会同时读**两个视角 | 只是主题相似，能合并                   |
| 两边的"前置知识"差很大，混在一起读会困惑         | 主题是同一段连续叙述，拆开要重复上下文 |
| 一边的内容**会快速更新**、另一侧很稳定     | 两边更新节奏一致                       |
| 用户能直接说出"我只需要 X 视角"                  | 读者没反馈过"想只看 X"                 |
| 一边有独立的"操作流程"或"判定标准"，另一侧没有   | 两边都是描述性的                       |

## 何时不切（哪怕表面像）

- "开发者"和"使用者"看起来对立，**但其实写的是同一段代码**——拆开会重复上下文
- 主题之间交叉引用 > 50%——合在一起读更顺
- 内容总长度 < 500 行——拆的引用成本 > 节省的注意力
- 你刚拆过一次主 ref，先**等 3 个月**看哪个 ref 真正被多次访问

## 验证方法（"我切对了吗？"）

切完之后，做这 3 件事验证，否则别动：

1. **覆盖率检查**：新 ref 是否覆盖了原 SKILL.md 100% 的内容（不能丢）
2. **读者路径测试**：找 2 个真实读者，**各只给一个 ref**，问"你能完成你的任务吗"——两人都能完成说明切对了
3. **访问统计**（如果有）：切之前先**埋点**记录每个 ref 的访问次数，3 个月后看是否真的分流了——没分流就合回去

## 反模式

| 反模式                       | 为什么坏                                       |
| ---------------------------- | ---------------------------------------------- |
| 凭"主题看起来不同"就切       | 读者常常需要同时读，强行切是给他们增加跳转成本 |
| 为了"显得专业"切出 5+ 个 ref | 注意力分散，**没人**真的读完             |
| 切了不更新索引表             | ref 成为孤儿文档，**再没人能找到**       |
| 切完没验证                   | 可能切错了，几个月后才发现                     |

## 速查决策表

```
你打算把"X 文档"切到第二层
  │
  ├─ X 是"主流程正文"还是"特化案例"？
  │   ├─ 主流程正文 → 不切（留在主 SKILL.md）
  │   └─ 特化案例 → 切到 references/
  │
  ├─ 已有读者反馈"只看 X 部分"吗？
  │   ├─ 有 → 强信号，切
  │   └─ 没有 → 弱信号，先观察 3 个月
  │
  ├─ 两边更新频率差 > 5 倍？
  │   ├─ 是 → 切（高频边独立演进）
  │   └─ 否 → 强合弱切
  │
  └─ 切完做 3 件事了吗（覆盖 / 路径 / 统计）？
      ├─ 是 → 落地
      └─ 否 → 回滚
```

## 与主 ref 的关系

- **本 ref 是 [[场景C-沉淀为ref]] 的"切分方法论"次级案例**，不是替代
- 调用顺序：先看场景 C（是否要拆 ref）→ 再看本 ref（拆了之后是否要分第二层）
- 本 ref 自身**不创建任何文件**——只回答"现在该不该切 / 切什么维度"的问题

## 一句话总结

**第二层切分是"读者路径工程"而不是"主题分类学"**。先有读者，再有分类。
