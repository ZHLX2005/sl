# Key Board 3 — Skill References 优化器

## 触发条件

| 用户说                                                            | 对应场景                   |
| ----------------------------------------------------------------- | -------------------------- |
| "把 xx 沉淀为 reference" / "拆到 references" / "单独存一下"       | ★ 场景 C（核心）          |
| "这个 skill 太大了 / 膨胀了" / "按子主题拆分" / "重构 skill 结构" | 场景 A                     |
| "给 skill 加 ref 引导" / "什么时候读哪个 ref，加一下"             | 场景 B                     |
| "统一所有 skill 的 ref 架构"                                      | 场景 D                     |
| "合并 skill" / "把多个 skill 合成一个"                            | 合并场景（特殊优化）       |
| "探索 / 扫描 / 观察现有 skill" / "哪些 skill 可合并"              | 场景 E（只出报告，不动手） |

场景到执行细节的路由，见下方「场景路由（ref-map）」。

## 核心原则

**主 SKILL.md 负责原则和 ref-map；references/ 才存放具体场景。**

### 角色分离

| 文档                      | 角色           | 只放                                                 | 不放                                             |
| ------------------------- | -------------- | ---------------------------------------------------- | ------------------------------------------------ |
| 主 SKILL.md               | 原则 + ref-map | 触发条件、核心原则、主流程 SOP、检查清单、场景路由表 | 任何场景级细节（完整步骤、示例、判定标准、案例） |
| references/<ref></ref>.md | 具体场景       | 某个场景的完整 SOP、示例、正反例、判定细节           | 通用原则（那是主文档的事）                       |

> ref 的定位是「特化专项的特化指导」：为某个特化场景提供独立、深入的按需指导，**不是为主文档减肥**。主题才是判据——既不为了拆而拆碎同主题内容，也不把异构主题硬塞进一个文档。

### 演化反模式（添加 ref 时最要警惕的坑）

一个 skill 的典型演化路径：

1. **v1**：还没有 ref，核心内容全部写在主 SKILL.md —— 此时是**合理的**（还没有更好的存放处）
2. **v2**：用户要求沉淀某主题 → 创建了 ref → **但主文档里的旧场景内容没有同步清空**
3. **结果**：主文档同时兼具「主题场景承载」和「ref-map」两种角色——一半正文、一半目录，行文混乱；此后每次扩展 ref 或合并 skill，混乱都在加深

**正确做法**：每次添加 ref 或合并 skill 时，被下沉主题的场景级内容必须**同步从主文档移除**，原位置只留一句原则总结 + `[[锚点]]`。主文档随 ref 增多而**变薄**，而不是变厚。

> 本 skill 自身就是按此终态组织的：你正在读的主文档 = 原则 + 路由表，全部场景的执行细节在 references/ 里。

### 边界

| 不做什么                                      | 做什么                                     |
| --------------------------------------------- | ------------------------------------------ |
| ❌ 不创建新 skill 目录                        | ✅ 按主题把 skill 组织成 主文档 + 特化 ref |
| ❌ 不修改前置 skill (key_board / key_board_2) | ✅ 在 SKILL.md 加 ref 加载引导             |
| ❌ 不改 skill 的核心流程/触发条件             | ✅ 允许轻度润色描述、补错误案例            |
| ❌ 不动 skill 的代码实现                      | ✅ 只搬文档结构                            |

**前置依赖**（不要变）：

- `key_board_2` — 创建 skill 的元模板
- `key_board_3`（本 skill）— 优化已有 skill 的结构

## 与 key_board_2 的核心区别（一句话）

> **key_board_2 创建新 skill，key_board_3 创建 references**。
> 一个是"建新楼"，一个是"拆老楼"。

## 场景路由（ref-map）

执行任何场景前，先在此表定位，再按需加载对应 ref：

| 场景                                                  | 信号                              | 何时读取                        | 路径                               |
| ----------------------------------------------------- | --------------------------------- | ------------------------------- | ---------------------------------- |
| ★**C：沉淀特定主题为 ref**（核心，触发最频繁） | "把 xx 沉淀为 reference"          | 触发场景 C 时                   | references/场景C-沉淀为ref.md      |
| A：SKILL.md 主题混乱                                  | "skill 太大了 / 膨胀了"           | 触发场景 A 时                   | references/场景ABD-结构优化.md     |
| B：补 ref 加载引导                                    | "给 skill 加 ref 引导"            | 触发场景 B 时                   | 同上                               |
| D：多 skill 统一 ref 架构                             | "统一 ref 架构"                   | 触发场景 D 时                   | 同上                               |
| E：合并候选审计（探索模式）                           | "扫一遍 / 哪些可合并"             | 触发场景 E 时（只出报告不动手） | references/场景E-合并审计.md       |
| 合并：多个 skill 合一                                 | "合并 skill"                      | 主流程判断**确需合并后**  | references/merge-skill-专项.md     |
| C 的次级：ref 树再切一层                              | 用户主动要求进一步切分现有 ref 树 | **不常驻**，仅明确要求时  | references/references-Diversion.md |

> **合并场景注意**：先走本 skill 主流程判断（是否真要合并？拆出去不行吗？），确认后才加载 [[merge-skill-专项]] 获得 4 阶段合并执行细节。合并产生的"新 skill"是合并动作的**副产品**，本职仍是"创建 references 和加引导"。

## 操作 SOP（5 步）

### Step 1: 识别作用域

问用户（或自己推断）：

- 目标 skill 是哪个？（路径）
- 触发的是哪个场景？（对照场景路由表）
- 是否限制不动某些章节？（如"前置 skill 不变"）

**如触发场景 E**（用户说"扫所有 skill / 哪些可合并 / 看看有没有重复"）：范围为 `.claude/skills/` 下所有 skill 目录，目标**只出审计报告**——立即加载 [[场景E-合并审计]]，按其模板生成报告；用户选定条目后，再回到 Step 1-5 执行具体条目。

### Step 2: 列出当前结构

读取目标 skill 的 SKILL.md，列出：章节大纲、是否已有 references/、已有 ref 数量。

**主题判断**：列完章节后，自问"这个 skill 是否真的承载了多个独立主题"。判据不是"内容多少"，而是"读这些章节的人，会不会因为场景不同而只读其中一部分"。是 → 拆；否 → 不拆。

### Step 3: 设计方案

按场景设计（各场景的完整设计要点在对应 ref 里）：

- **场景 C/A**：ref 名称、文件路径、加载时机、为什么这是个独立主题
- **场景 B**：只在末尾加引导段
- **场景 D**：先选模板 skill

### Step 4: 执行

加载场景路由表中对应场景的 ref，按其 SOP 执行。共同骨架：

- 建 `references/<ref-name>.md` → 完整迁移内容 → 原位置留 `[[锚点]]` + 一句总结 → 末尾索引表登记
- **下沉必须彻底**：主文档中该主题的场景级内容同步清空，杜绝"ref 里存新内容、正文里还留一份旧步骤"

### Step 5: 校验

对照下方「成功标准检查清单」逐项过。结构类硬校验：

- [ ] 主文档无场景级内容残留（每章要么是原则、要么是路由）
- [ ] 每条索引写的是"何时读取"，不是内容总结
- [ ] 没有遗留空 ref 文档

## 易错和坑（高频错误）

| 错误                                  | 根因                       | 预防                                                                      |
| ------------------------------------- | -------------------------- | ------------------------------------------------------------------------- |
| **加 ref 后主文档旧内容不清空** | 以为"建了 ref 就完事"      | 演化反模式：主文档会兼具场景承载和 ref-map 双角色；下沉必须同步清空原位置 |
| 给单 skill 强行套 references/         | 单 skill 不需要 ref 子目录 | 主题没独立价值时不要硬拆                                                  |
| ref 文档没有加载引导                  | 以为 ref 自己会被读        | SKILL.md 路由表必须写"何时读这个 ref"                                     |
| 把 ref 名和文件名弄混                 | 链接不规范                 | `[[ref-name]]` 中的 name 必须等于文件名                                 |
| 拆得太碎（一个章节一个 ref）          | 过度优化                   | ref 主题必须有独立价值，不是为了拆而拆                                    |
| 顺手改了 skill 核心流程               | 越权润色                   | 本 skill 只做结构，核心流程/触发条件禁止动                                |
| 把前置 skill 也"优化"了               | 忘记边界                   | key_board / key_board_2 是不可变的                                        |
| 把主流程步骤也拆出去                  | 误以为所有内容都可沉淀     | 主流程、触发条件、检查清单必须留在主 SKILL.md                             |
| 拆完忘记登记索引表                    | ref 成为孤儿文档           | Step 4 强制末尾索引登记                                                   |

## 成功标准检查清单

- [ ] **主 SKILL.md 只含原则与 ref-map，无场景级内容残留**（每章要么是原则、要么是路由）
- [ ] 主题在主文档和 ref 之间分配清晰、不重复
- [ ] 所有 ref 在路由表登记，且写明"何时读取"
- [ ] `[[ref-name]]` 链接与文件名一一对应
- [ ] 前置 skill (key_board / key_board_2) 未变
- [ ] 目标 skill 的核心流程/触发条件未变
- [ ] 没有空 ref 文档
- [ ] 用户确认了拆分方案（如未明确授权）

## 何时**不**触发本 skill

- 用户想**创建新 skill** → 用 key_board 或 key_board_2
- 用户想**改 skill 的代码/实现** → key_board_3 不管代码
- 用户想**优化 skill 触发描述**（description 字段） → 用 `skill-creator` 的 description 优化流程
- 用户想**评估/量化 skill 效果** → 用 `skill-creator` 的 eval 流程
- 目标 skill 无独立主题 → 不要硬拆，劝退

## 与其他 skill 的协作

```
key_board_2    →  用元模板创建 skill (从 0 到 1 的标准流程)
key_board_3    →  优化已有 skill 的结构 (从 1 到 N 的演化)
skill-creator  →  评估/优化/打包 skill (质量保障)
```

key_board_3 在演化链路上，承接 key_board_2 创建出来的 skill，做后续结构优化。
