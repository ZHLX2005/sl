# a02 线程上下文传值与透传 —— 请求级业务数据的隐式传递与生命周期

> 通用代码设计规范，与语言、框架无关。

## 规范命题

**请求级业务数据应当在生命周期受控的隐式通道里 “透传”，而不是逐层写进函数签名。**

显式传参的代价：一个 `tenantId` 从 Controller 传到 Service 传到 Repository，中间每个函数签名都要带上；新增一个上下文值要改一整条调用链；上下文参数与业务参数混杂，签名越滚越长。

隐式通道（thread-local / request context / async-local storage）让中间层 “不感知但可读”—— 这是它的价值，也是它的危险：**隐式通道本质是隐藏的全局可变状态**。它有两个致命风险：**泄露** 与 **池化串扰**。

**一句话纪律：隐式通道必须 “请求边界设置 → 请求出口清理”，且永远不能与全局对象或复用单元（线程 / 协程 / 连接）的生命周期混同。**

## 透传的载体（跨语言对应）

| 语言 / 运行时 | 载体 | 生命周期锚点 |
| --- | --- | --- |
| Java | `ThreadLocal` / `InheritableThreadLocal` | 请求线程；线程池复用 → 必须 `finally remove` |
| Go | `context.Context` | 请求调用树；`defer cancel()` |
| Node / JS | `AsyncLocalStorage` | 异步调用链；`run()` 作用域 |
| Python | `contextvars.ContextVar` | 协程 / task |

共性：载体必须绑定到**一次请求 / 一次调用树**，而不是绑定到**承载它的执行单元**（线程、goroutine、连接）。把两者绑死，就是一切串扰事故的源头。

## 案例 A：上下文驱动的 SQL 谓词下推（多租户 SaaS）

**场景**：多租户系统，每次查询都要带 `tenant_id = ?` 条件。若靠业务手写，新写的查询忘带就是跨租户数据穿透。

**做法（谓词下推）**：

1. 入口（Filter / Interceptor / 中间件）从认证信息解析出租户，放进**请求上下文**；
2. 在**数据访问出口层**（SQL 改写拦截器 / ORM 插件）统一读取上下文里的租户，把 `tenant_id` 谓词**自动拼进每条 SQL 的 WHERE**；
3. 业务代码不写租户条件，也拿不到租户变量 —— 从结构上杜绝 “忘带”。

**与 a01 的接力**：a01 说 “横切规则在出口层统一改写”，a02 补上前一个问题 —— **规则所需的数据从哪来**。答案是：它来自请求上下文，且**只在该请求生命周期内有效**。

**为什么下推放在出口层而不是业务层**：业务层不该、也拿不到租户；出口层能保证 “每条 SQL 都过一遍”，不漏。

**反例（最严重的一类事故）**：

- 把租户存进全局 `Map<threadId, tenant>` 或静态字段 → 线程池复用线程时，下一个请求读到上一个租户 → **跨租户数据泄露**，且日志里看不出来；
- 拦截器里取租户取到空就 “不加条件” 放行 → 等于全表查询。必须 fail-fast（与 a01 一致）。

## 案例 B：Go 的 context 传值

```go
// 入口注入
ctx = ctxbiz.WithTenant(ctx, &ctxbiz.Tenant{TenantID: tid})

// 下游读取（出口层 / 横切组件）
t, ok := ctxbiz.GetTenant(ctx)
if !ok {
    return nil, fmt.Errorf("tenant context not found") // 缺值 fail-fast，不静默放行
}
```

要点（Go 的完整实现与字段约束见 [[b02-go-ctx-register]]）：

- ctx key 用**空 struct 实例**（类型安全），值用指针，`Get` 返回 `(*T, bool)`；
- ctx 只传**请求元数据与配置**，不传实例、不传业务大对象；
- **不要把 ctx 存进 struct 字段** —— ctx 是一次调用树的载体，存进长生命周期对象等于让它的生命周期逃逸（`go vet` 会就 `context` 误用告警）。

## 核心风险：泄露与池化

### 风险 1：未清理 → 内存泄漏 + 陈旧数据

`ThreadLocal` 若不 `remove`：entry 一直挂在**线程对象**的 map 上，而池化线程近乎永生 → 值不被回收（内存泄漏）；下一个请求复用该线程时读到**上一个请求的残留值**（数据串扰）。

### 风险 2：池化复用 → 上下文串扰

线程池 / goroutine 复用 / 连接池 让 “执行单元” 的生命周期远长于 “请求”。任何把请求上下文**附着在执行单元上**的设计，都会在复用点串扰。**池化程度越高，串扰越难复现、越像鬼故事**。

### 风险 3：异步 / 并发传递丢失或错乱

- 普通 `ThreadLocal` **不会**自动传播到线程池里的子任务 → 子线程读到 null 或父线程旧值。`InheritableThreadLocal` 只在 “新建线程” 时复制，**线程池下依然失效** —— 必须显式传递（提交任务时捕获再包装，或把值作为参数传进任务）。
- 多路并发写同一个隐式通道 → 数据竞争。

### 风险 4：与全局对象混同

把请求上下文塞进**静态字段 / 全局单例 / 池化对象的字段** → 等于把 “每请求的值” 升级成 “全局可变状态”，多请求互相覆盖。**这是把风险 2 从 “偶发” 变成 “必然”。**

## 正确做法：边界设置 → 出口清理

**Java —— ThreadLocal 必须 `finally` 清理**：

```java
try {
    RequestContext.setTenant(tenant);
    chain.doFilter(req, resp);
} finally {
    RequestContext.clear();   // 必须：池化线程上不 clear 就是泄露 + 串扰
}
```

**Go —— context 用 `defer cancel()` 回收**：

```go
ctx, cancel := context.WithCancel(parent)
defer cancel()   // 及时释放，避免 goroutine / 定时器 / 子节点泄漏
```

**Node —— `AsyncLocalStorage.run` 让作用域随回调自动回收**：把整条异步链包在 `storage.run(value, fn)` 里，不要手工 `set` / 手工清理配对。

**通用规则**：

- 设置点与清理点**成对出现**，且清理点必须在 `finally` / `defer`（异常路径也要回收）；
- 清理用 `remove()` / `clear()`，**不要用 `set(null)`**（残留引用仍在 map 上）；
- 清理后该上下文不可再用；跨请求**绝不共享**同一份上下文。

## 边界与变体

| 情况 | 处理 |
| --- | --- |
| 通用库 / 纯函数 | 不应隐式依赖线程上下文（库会变成 “依赖当前线程状态”）；改为显式收参或显式收 ctx |
| 需要在入口之外读上下文 | 只允许在出口层 / 横切组件读；业务核心逻辑显式收参 |
| 异步任务需要上下文 | 提交任务时**显式捕获并传递**（包装 Runnable/Callable，或把值作为参数传进 goroutine），不依赖继承 |
| 上下文值可变性 | 放入后视为**只读**；要改就派生新的（Go 的 ctx 天然不可变） |
| 线程池 + ThreadLocal | 优先用框架级请求作用域（RequestScope）而非裸 ThreadLocal |
| 池化对象（连接 / 缓存） | 禁止持有请求上下文 —— 会把请求值带进全局 |
| 取不到值 | 明确语义：fail-fast 抛错，或由调用方显式处理；禁止静默放行 |

## 错误案例

| 错误操作 | 实际后果 | 正确做法 |
| --- | --- | --- |
| entry 设置后不清理 | 池化线程内存泄漏 + 跨请求读到旧值 | 出口 `finally` / `defer` 清理 |
| entry 用 `set(null)` 清理 | 残留引用，仍挂在 map 上 | 用 `remove()` / `clear()` |
| 清理写在 `try` 体内（非 `finally`） | 异常路径不回收 | 清理放 `finally` / `defer` |
| 上下文放进静态字段 / 单例 | 全局可变状态，多请求互相覆盖 | 只放在线程 / 请求作用域 |
| 依赖 ThreadLocal 传到线程池子任务 | 子线程读不到或读到旧值 | 显式捕获传递（包装 / 作为参数） |
| Go 把 ctx 存进 struct 字段 | 生命周期逃逸，取消 / 超时失效 | ctx 只做函数首参与逐层传递 |
| Go 调了 `WithXxx` 不 `cancel` | goroutine / 定时器泄漏 | `defer cancel()` |
| 拦截器取不到上下文就放行 | 漏加租户条件 = 全表 / 跨租户查询 | fail-fast |
| 用上下文传业务大对象 / 实例 | 职责混乱 + 生命周期失控 | 只传请求级元数据 / 配置 |

## 判定五问（评审时逐条问）

1. 这个隐式通道的值，是在**请求边界设置、请求出口清理**的吗？（不是 → 泄露风险）
2. 清理用的是 `remove()` / `clear()`，且放在 `finally` / `defer` 吗？（异常路径也回收吗？）
3. 有没有任何**全局对象 / 单例 / 池化对象**持有它？（有 → 全局污染）
4. 需要跨线程 / 协程 / 异步任务时，是**显式传递**还是依赖自动继承？（依赖继承 → 池化下必错）
5. 取不到值时的行为是 **fail-fast** 还是静默放行？（静默放行 → 数据穿透）

## 检查清单

- [ ] 隐式通道只在请求边界设置、出口清理；清理在 `finally` / `defer`，用 `remove()` / `clear()`
- [ ] 没有任何全局 / 静态 / 单例 / 池化对象持有请求上下文
- [ ] 需要异步 / 并发传递时靠**显式捕获**，不依赖线程继承
- [ ] 上下文只承载请求级元数据 / 配置，不放大对象与实例
- [ ] 出口层（如 SQL 改写）读上下文缺值时 fail-fast，不静默放行
- [ ] 通用库 / 纯函数不隐式依赖线程上下文
