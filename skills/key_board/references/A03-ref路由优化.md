# ref 路由优化 — 序列化命名模式

> **触发门槛**：ref 数量 > 5。少于等于 5 个时保持平铺命名（如 `沉淀为ref.md`），不为编号而编号。
>
> ref 数量超过 5 后，平铺命名的路由表会退化为无结构清单——读者扫一眼分不出"哪些 ref 属于同一类动作"。本 ref 解决的就是这个问题：**用序列代号给 ref 建立一层"类别索引"**，主文档 ref-map 通过代号即可表达分类。

## 编号规则

格式：`<序列字母><两位序号>-<名称>.md`

```
A00-结构演化路由.md     ← 00 = A 序列元数据
A01-沉淀为ref.md        ← 01 起 = 动作 ref
A02-结构优化.md
A03-ref路由优化.md
B00-合并路由.md         ← 00 = B 序列元数据
B01-合并审计.md
B02-合并执行.md
C01-创建新skill.md      ← 单成员序列：00 可省，直接 01
```

| 组成 | 规则 | 示例 |
| --- | --- | --- |
| 序列字母 | 大写字母，一个序列 = 一个动作类别 | `A` |
| 序号 `00` | **保留给序列元数据 ref**：该序列的详细 route 信息（序列内信号→成员路由、成员边界、升级路径） | `A00-结构演化路由.md` |
| 序号 `01` 起 | 动作 ref，按主次/流程顺序递增 | `A01`、`A02` |
| 名称 | 保留语义名，连字符连接；**文件可读性优先，不搞纯代号** | `A01-沉淀为ref.md` 而非 `A01.md` |

**为什么保留原名称**：纯代号（`A01.md`）要求读者先查 ref-map 才知道内容是什么，多一次跳转；代号 + 名称的文件名自带语义，`ls references/` 一眼可读。

**00 元数据 ref 的取舍**：多成员序列（≥2 个动作 ref 且存在边界混淆风险）才建 `X00`；单成员序列（如 C）直接从 `01` 起，不为凑格式造空 ref。元数据 ref 自身**不承载动作 SOP**，只收敛"序列内路由"——它让主文档 ref-map 保持一行一序列的粒度，把"该进序列哪个成员"的判断下沉到序列入口。

## 序列划分原则

**按「读者 / 动作类别」划分，不按主题词划分。**

- 序列 = 一类读者或一类动作。例：A 序列 = 结构演化类动作，B 序列 = 合并类动作，C 序列 = 创建类动作
- 每序列内 `01` 给最高频/主流程的 ref，后续按流程顺序递增
- 判断标准沿用 [[A01-沉淀为ref]] 第二层切分的读者路径判据：**"读这些 ref 的人，会不会因为场景不同而只读其中一个序列？"** 是 → 分不同序列；否 → 塞同序列

**反例**：按文件名字母序编号、按创建时间编号——编号应承载分类信息，不是流水号。

## 主文档结构：序列先于 ref 明细

主 SKILL.md 中，**序列图例必须放在 ref-map 明细表之前**——读者先建立"字母 = 类别"的心智映射，再读逐行明细，而不是读完全部明细才回头理解代号：

```markdown
## 序列总览（先读这里）

| 代号 | 类别 | 成员 |
| --- | --- | --- |
| A | 结构演化 | [[A00-结构演化路由]]（入口）→ A01 沉淀为ref / A02 结构优化 / A03 ref路由优化 |
| B | 合并 | [[B00-合并路由]]（入口）→ B01 合并审计 / B02 合并执行 |
| C | 创建 | C01 创建新skill（单成员，无元数据 ref） |

## 场景路由（ref-map 明细）

| 场景 | 信号 | 何时读取 | 代号 | 路径 |
| --- | --- | --- | --- | --- |
| ... | ... | ... | ... | ... |
```

明细表每行的「代号」列与总览表对应；有元数据 ref 的序列，其入口即 `X00` 文件——读者只需记住"进 A 序列先看 A00"。

## 执行 SOP（对已有 skill 做序列化改造）

### Step 1: 盘点与划分

1. 列出 `references/` 全部 ref 及各自职责
2. 按动作类别归组，产出序列划分表（字母 → 类别名 → 成员）
3. 序列数控制在 **2-4 个**：超过 4 个说明分类维度太细，读者记不住字母含义
4. 逐序列判断是否需要 `X00` 元数据 ref（多成员 + 有边界混淆 → 建；单成员 → 跳过）

### Step 2: 建元数据 ref + 重命名动作 ref

```bash
# 有元数据的序列：新建 X00
# 动作 ref 全部重命名为 X01 起
git mv references/<原名>.md references/<代号>-<原名>.md
```

**注意**：用 `git mv` 保留历史；同批全部重命名，不留半编号半平铺的混合态。

### Step 3: 全量修正 [[链接]]

`[[原名称]]` 链接全部改为 `[[代号-原名]]`，范围包括：

- 主 SKILL.md（序列总览、ref-map、路由优先级、易错表、正文锚点）
- 所有 ref 文件内部互引 + 仓库内其他 skill 的跨 skill 引用

用 Grep 搜旧名确认零残留。

### Step 4: 主文档加「序列总览」+ ref-map 加「代号」列

按上文「主文档结构」模板：序列总览表放 ref-map **之前**。**主文档只加一表一列，不新增场景级章节**——序列信息由代号列和总览表承载，主文档行数不因此增长。

### Step 5: 校验

- [ ] 动作 ref 全部 `X01` 起编号；`X00` 仅用于序列元数据 ref
- [ ] 元数据 ref 只含序列内路由，不含动作 SOP；无空 ref
- [ ] 序列数 2-4 个，每序列有明确类别名
- [ ] 主文档**序列总览在 ref-map 明细之前**，明细表有「代号」列
- [ ] `[[旧名]]` 链接零残留（Grep 验证，含仓库内跨 skill 引用）
- [ ] 主文档未新增场景级章节，仍只含原则 + ref-map
- [ ] 核心流程/触发条件未变

## 扩展时如何续号

- 新 ref 属于已有类别 → 沿用序列字母，取该序列 max 序号 +1（如 A03 之后加 A04）
- 新 ref 是全新类别 → 启用新字母，动作从 `D01` 起（`D00` 留给潜在元数据）
- 序列被合并/废弃 → 字母不复用给新类别（避免历史代号指向漂移），宁可跳号
- 序列内成员多到边界频繁混淆 → 说明 `X00` 元数据 ref 需要扩充路由行，而不是继续加成员

## AI 生成代码 Top错误事项(不超过5)

| 错误 | 后果 | 预防 |
| --- | --- | --- |
| ref ≤ 5 也强行编号 | 编号不承载信息，纯噪音 | 严守 >5 门槛 |
| 单成员序列也造 `X00` 元数据 ref | 空壳 ref，无人读 | 多成员 + 有边界混淆才建；单成员直接 01 |
| 动作 ref 从 `00` 起编号 | 00 被动作占用，元数据无处安放 | 00 恒为元数据保留位，动作一律 01 起 |
| 主文档把 ref 明细表放在序列总览之前 | 读者对着代号读明细，读到一半才懂字母含义 | 总览先行，明细随后 |
| 重命名后漏改 [[链接]]（含外部 skill） | 孤儿链接，路由断裂 | Grep 旧名全仓零残留后才算完成 |
