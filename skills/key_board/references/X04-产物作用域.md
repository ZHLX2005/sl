# X04 — 产物作用域（通用级 / 项目级）

> **使用条件**：任何"要往 skill 里写内容"的动作**动手前**——创建新 skill（[[Z01-创建新skill]] / [[Z02-代码库创建skill]]）、把内容沉淀进 ref（[[X01-沉淀为ref]]）。
>
> 本 ref 只回答一个问题：**这份产出该带多少上下文？** 它不判断内容对不对，只判断"上下文密度"和"作用域"是否匹配。

## 为什么需要这道闸

skill 会被传播：复制到别的仓库、装进别人的 agent、被另一个项目调用。传播时**只有一个 SKILL.md 跟着走，作者脑中的项目上下文不会跟着走**。

于是出现两类高频缺陷：

| 缺陷 | 现象 | 后果 |
| --- | --- | --- |
| **上下文泄漏** | 通用 skill 里写着项目名、绝对路径、"参考 XX 项目 / 某内部文档" | 读者的环境里对不上任何一个专有名词，每条都成了死链接 |
| **上下文缺失** | 项目级 skill 里用 `<模块名>`、`<目标目录>` 这类占位符 | 读者（未来的 AI / 新同事）无法执行，等于没写 |

两者根因是同一个：**写之前没有声明作用域**。

## Step 1: 判定作用域（三连问）

依次问，**任一为"是"即判为项目级**：

1. 内容里的名字（项目名 / 模块名 / 表名 / 接口名）**换掉一个**，这份 skill 还成立吗？→ 不成立 = 项目级
2. 别人（或别的仓库的 AI）拿到它，**不需要访问作者的环境**就能照着执行吗？→ 不能 = 项目级
3. 它的触发时机是否依赖某个**具体目录 / 仓库 / 服务**的存在？→ 依赖 = 项目级

| 作用域 | 一句话 | 典型例子 |
| --- | --- | --- |
| **通用级** | 换个项目 / 机器 / 同事，仍然成立 | `tool-isolation`、`cli-standard`、`key_board`，以及任何"方法论 / 流程 / 规范"型 skill |
| **项目级** | 脱离这个项目就没有意义 | 某仓库的模块规范、某私有服务的部署 SOP、某系统的字段字典 |

> **按 ref 粒度判，不要一刀切**：一个 skill 里不同部分可能作用域不同。主文档是通用方法论、某个 ref 是某项目的具体配置——就在那个 ref 的头部单独声明适用范围，不要为了"统一"把整包升格或降级。

## Step 2: 红线一 —— 通用级 = 零项目上下文

通用级 skill 里**禁止出现**：

| 类别 | 例子 | 改法 |
| --- | --- | --- |
| 项目 / 仓库 / 服务名 | `dev_ctr_hello`、`encryptkv`、内部代号 | 删掉，或抽象为"目标项目" |
| 绝对路径 | `D:\a_go\proj_1\...`、`/Users/xxx/...` | 改 `<项目根>/api`，并在首次出现处说明这是占位符 |
| 人名 / 工号 / 客户名 | 真实姓名 | 删除或泛化 |
| 内部术语 / 黑话 | 只在某个团队内部流通的说法 | 换成通行表述 |
| 一次性时间锚点 | "上周那次事故"、"2026-10-08 的变更" | 抽成判据，去掉时间 |
| **来源句** | "参考 XX 项目的经验"、"按 nx-kv 的方式"、"从某内部文档抄的" | 见下 |

**来源句必须剥掉**，这是最容易被忽略的一类：

- 作者写下来源时觉得"有出处更可信"，但读者**没有那个上下文**——来源对他不是证据，是死链接。
- 正确做法：把来源里**可复用的判据**抽出来，来源本身删除。

```
❌ 参考 XX 项目的经验，提交前要跑 lint
✅ 提交前必须跑 lint（否则 CI 会红）      ← 判据留下，出处无关
```

**允许出现的"具体值"**：公开、人人可得的生态名词不算项目上下文——`package.json`、`.gitignore`、`npm link`、`/usr/bin`、HTTP 状态码。判据一句：**这个具体值是不是"只有在作者的环境里才成立"**。

## Step 3: 红线二 —— 项目级 = 用当前项目的信息来写

**只有项目级 skill 才允许、且必须使用当前项目的信息**（项目名 / 仓库根 / 真实路径 / 模块名 / 内部约定的名称）。它的目标就是**在这个项目里可执行**，上下文不是污染，是必需品：

> **反向对照**：通用级 skill **一律不使用当前项目的信息**——一旦出现项目名 / 绝对路径 / 内部术语 / 来源句，就说明作用域判错了，回 Step 2 处理。

1. **头部声明适用范围**：`> 本 skill 仅适用于 <项目名>（<仓库根>）。` —— 防止传播后被误用到别的项目
2. **路径 / 模块名写真实值**：占位符在这里等于没写。能写绝对路径就写绝对路径；用仓库内相对路径时必须交代"相对谁是根"
3. **必要的环境信息写全**：技术栈与版本、内部约定的名称——因为读者没有这个项目的记忆
4. **不要为了"看起来通用"而抽象**：把真实路径换成 `<模块名>` 不会让 skill 更通用，只会让它不可执行

## 一句话判据

> **作用域声明决定上下文密度**：通用级零上下文（用占位符），项目级满上下文（用真实路径）。
> 出现「局部项目概念或来源」却又是通用 skill → 就是作用域错配。

## 反例（全部来自真实产出）

| 现象 | 错在哪 | 改法 |
| --- | --- | --- |
| 通用 skill 里写 `D:\a_go\proj_1\dev_ctr_hello\api` | 绝对路径绑死作者的机器 | 改 `<项目根>/api`，并声明是占位符 |
| 通用 skill 里写"用法同 nx-kv" | 依赖读者环境里恰好装了另一个 skill | 内联成自包含描述，或声明为**产物层依赖**（见 [[Z01-创建新skill]]） |
| 通用 skill 里写"这是给 encryptkv 做的" | 来源对读者无用 | 删除来源句 |
| 通用 skill 里写"按我们团队的 XX 规范" | 内部黑话，外部不可解 | 把规范内容写出来，而不是引用名字 |
| 项目级 skill 写 `<模块目录>/handler.go` | 占位符让 skill 无法执行 | 写真实路径 |
| 项目级 skill 未声明适用范围 | 被误用到其他项目 | 头部加"仅适用于 X" |

## 检查清单

- [ ] 已判定作用域（三连问答得上），并在产出中体现
- [ ] 通用级：无项目 / 仓库 / 服务名，无绝对路径，无人名，无内部术语，无一次性时间锚点
- [ ] 通用级：无来源句；原有来源里的经验已抽象为可复用判据
- [ ] 通用级：占位符统一，且首次出现处有说明
- [ ] 项目级：头部有"仅适用于 X"的适用范围声明
- [ ] 项目级：关键路径 / 模块名是真实值，未用占位符糊弄
- [ ] 逐句过了"换个项目 / 换台机器，这句还成立吗"

## 边界

| 不做 | 做 |
| --- | --- |
| ❌ 不判"内容对不对" | ✅ 只判"上下文密度与作用域是否匹配" |
| ❌ 不禁止通用 skill 举例子 | ✅ 例子要自包含，不引用读者拿不到的东西 |
| ❌ 不把项目级 skill 硬改通用 | ✅ 项目级就明写上下文 + 声明适用范围 |
