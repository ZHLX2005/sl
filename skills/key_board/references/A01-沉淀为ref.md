# 沉淀为 ref — 拆解与分层

> **key_board 触发最频繁的动作**。听到"沉淀为 reference / 拆出去 / 单独存一下"，第一时间走本流程。
>
> **主流程骨架**（识别作用域 / 列当前结构 / 校验）见主 SKILL.md 的 5 步；本 ref 从 Step 3「设计方案」开始细化。

## 创建新 skill 不是本动作

| 动作 | 触发信号 | 加载 ref |
|---|---|---|
| **创建新 skill**（从 0 到 1） | "总结成 skill" / 无现有 ref 可扩展时 | [[C01-创建新skill]] |
| **沉淀为 ref**（拆老楼） | "沉淀为 reference / 拆出去 / 单独存" | 本 ref |

> **一句话总结**：创建新 skill 是从 0 起楼，沉淀为 ref 是给老楼加 ref。两者走不同 ref，但都是 key_board 的子动作。

## 完整 SOP

### Step 1: 识别主题

读取目标 skill 的 SKILL.md，定位要沉淀的内容：

- 是哪一章？起止行号？
- 主题是否可以独立成立？（有明确触发时机 + 独立价值）
- 适合沉淀的常见主题：
  - 错误案例库（持续累积，独立价值高）
  - format 规范（写新 skill 时才查）
  - 调用细节 / API 速查（执行具体步骤时查）
  - 反思方法论（评估阶段才用）

**反例**：不要把"成功标准检查清单"沉淀为 ref——它每次创建 skill 都要用，跟着主流程走才对。

### Step 2: 设计 ref 文档结构

```markdown
---
name: <ref-name>
description: <一句话说清这个 ref 是干什么的、什么时候读>
---

# <Ref 标题>

## 加载时机
（什么时候必须读这个 ref？主 SKILL.md 哪个流程步骤？）

## 详细内容
（完整迁移过来的内容）

## 关联引用
（用 [[xxx]] 链接到主 SKILL.md 或其它 ref）
```

**注意 frontmatter 的 description**：写"什么时候读"，不要写"内容总结"。

### Step 3: 迁移内容

- 把原 SKILL.md 中的目标章节**完整**复制到 `references/<ref-name>.md`
- 复制时保持原有结构不变
- 修正内部链接：用 `[[ref-name]]` 形式（如果有引用其它 ref）
- 删除：任何已下沉的过时的、重复的、对其它 ref 的反向引用

### Step 4: 在主 SKILL.md 留锚点

在原章节位置（不要删除章节标题，只清空内容或留一句总结），写：

**下沉必须彻底（角色分离）**：不要 ref 里放新内容、正文里还留一份"旧版步骤"。主 SKILL.md 负责原则和 ref-map，ref 才存具体场景——原位置的场景级内容（操作步骤、示例、判定细节）全部进 ref，正文只留一句原则总结 + 锚点。

```markdown
详见 [[<ref-name>]]。
```

或者更详细：

```markdown
> 📎 **本节详细内容已沉淀到 [[<ref-name>]]**。
>
> 何时读：[填写具体的加载时机，如"创建新 skill 时 / 评估阶段 / 用户明确要求时"]
```

### Step 5: 在主 SKILL.md 末尾登记索引

如果还没有 ref 索引表，新增一个章节：

```markdown
## 引用索引（按需加载）

| ref | 何时读取 | 路径 |
|---|---|---|
| [[<ref-name>]] | [一句话说明加载时机] | references/<ref-name>.md |
| [[<ref-name-2>]] | [一句话说明加载时机] | references/<ref-name-2>.md |
```

如果已有索引表，补一行即可。

## 完成后必须验证

- [ ] `references/<ref-name>.md` 已创建
- [ ] 文件 frontmatter 完整（name + description）
- [ ] description 写"什么时候读"，不是"内容总结"
- [ ] 主 SKILL.md 原位置有 `[[ref-name]]` 锚点
- [ ] 主 SKILL.md 末尾 ref 索引表已登记
- [ ] 主文档原位置无该主题的场景级内容残留（只剩原则 + 锚点）
- [ ] 主题划分合理（每个 ref 都对应一个独立的特化场景）
- [ ] 核心流程/触发条件**没有**改动

## AI 生成代码 Top错误事项(不超过5)

| 错误 | 后果 | 预防 |
|---|---|---|
| 加 ref 后主文档旧内容不清空 | 主文档兼具"场景承载 + ref-map"双角色，行文混乱且持续恶化 | 下沉必须同步清空原位置，只留原则 + 锚点 |
| 把"成功标准"或主流程步骤也拆出去 | 创建流程失去完整性，主骨架被拆散 | 只有低频、专项内容才拆；主流程/触发条件/检查清单留在主文档 |
| ref 内不放加载时机 | AI 不知道什么时候读它，ref 成为死文档 | 每个 ref 开头必有"加载时机"，且在主文档路由表登记 |
| 拆得太碎（一个章节一个 ref） | 跳转成本 > 注意力收益 | ref 主题必须有独立价值，不是为了拆而拆 |
| 把主 SKILL.md 章节标题也删了 | 失去导航锚点 | 只清空内容，标题保留 |

## 典型适用场景

- ✅ 错误案例库（高频累积、内容多、有独立价值）
- ✅ 格式规范（写 frontmatter 时才查、用时短）
- ✅ API 速查（执行具体步骤时按需查）
- ✅ 反思方法论（评估阶段才用、可以独立深挖）
- ✅ 子领域/子框架的差异化细节（多领域 skill 才需要）

## 批量模式：skill 膨胀了 / AI 主动发现多主题

**信号**：多个子主题挤在一起（通常是用户说"这个 skill 太大了 / 膨胀了"）。

**与单主题模式的关系**：批量模式是"AI 主动发现多个主题要拆"，上面的单主题 SOP 是"用户点名一个主题要拆"。批量模式识别出主题后，**每个主题的迁移动作都走本 ref 的 Step 1-5**；批量模式只多了"先识别有哪些主题"这一步：

1. 列出 SKILL.md 全部章节，识别可独立主题
2. 为每个主题创建 `references/<ref-name>.md`
3. 内容迁移 + 留 `[[ref-name]]` 锚点
4. 按主题自然分配，不为了拆而拆

**主题识别判据**（同主 SKILL.md Step 2）：不是"内容多少"，而是"读这些章节的人，会不会因为场景不同而只读其中一部分"。是 → 拆；否 → 不拆。

**拆完后必须做角色分离检查**：主文档残留的场景级内容（步骤/示例/判定细节）一律下沉，主文档每章只留原则或路由。

## 进阶：第二层切分

> **本节不常驻读取。** 当主切分（要不要拆 ref）已经决定、且 ref 树已存在，用户进一步要求"再切一层"时才读本节。

**一句话原则**：已经决定"按主题拆 ref"之后，第二层问题永远是"按什么维度再切"。

### 三种常见的分层维度

| 维度 | 适用场景 | 例子 |
| --- | --- | --- |
| **按角色** | 同一 skill 文档既被"底座开发者"也被"插件作者"读，但诉求不同 | `core-developer/`（基座/源码/扩展）vs `plugin-developer/`（插件契约/scaffold/walkthrough） |
| **按场景** | 一个 ref 覆盖了"主流程 + 多个特例"，特例需要单独深入 | 主 ref（沉淀 SOP）vs 次级 ref（分层的判断方法论） |
| **按受众/介质** | 同一主题对"读者"和"写者"诉求不同 | "如何使用（consumer 视角）" vs "如何构建（author 视角）" |

> **维度选错了的代价**：分错了之后**读者找不到**——比"不切"还糟。
> 所以第二层切分必须用**读者路径**来验证，而不是按主题相似度。

### 何时切第二层（强信号）

| 强信号 | 弱信号（先别切） |
| --- | --- |
| 读者明确分两类人，**没人会同时读**两个视角 | 只是主题相似，能合并 |
| 两边的"前置知识"差很大，混在一起读会困惑 | 主题是同一段连续叙述，拆开要重复上下文 |
| 一边的内容**会快速更新**、另一侧很稳定 | 两边更新节奏一致 |
| 用户能直接说出"我只需要 X 视角" | 读者没反馈过"想只看 X" |
| 一边有独立的"操作流程"或"判定标准"，另一侧没有 | 两边都是描述性的 |

### 何时不切（哪怕表面像）

- "开发者"和"使用者"看起来对立，**但其实写的是同一段代码**——拆开会重复上下文
- 主题之间交叉引用 > 50%——合在一起读更顺
- 内容总长度 < 500 行——拆的引用成本 > 节省的注意力
- 你刚拆过一次主 ref，先**等 3 个月**看哪个 ref 真正被多次访问

### 验证方法（"我切对了吗？"）

切完之后，做这 3 件事验证，否则别动：

1. **覆盖率检查**：新 ref 是否覆盖了原 SKILL.md 100% 的内容（不能丢）
2. **读者路径测试**：找 2 个真实读者，**各只给一个 ref**，问"你能完成你的任务吗"——两人都能完成说明切对了
3. **访问统计**（如果有）：切之前先**埋点**记录每个 ref 的访问次数，3 个月后看是否真的分流了——没分流就合回去

### 反模式

| 反模式 | 为什么坏 |
| --- | --- |
| 凭"主题看起来不同"就切 | 读者常常需要同时读，强行切是给他们增加跳转成本 |
| 为了"显得专业"切出 5+ 个 ref | 注意力分散，**没人**真的读完 |
| 切了不更新索引表 | ref 成为孤儿文档，**再没人能找到** |
| 切完没验证 | 可能切错了，几个月后才发现 |

### 速查决策表

```
你打算把"X 文档"切到第二层
  │
  ├─ X 是"主流程正文"还是"特化案例"？
  │   ├─ 主流程正文 → 不切（留在主 SKILL.md）
  │   └─ 特化案例 → 切到 references/
  │
  ├─ 已有读者反馈"只看 X 部分"吗？
  │   ├─ 有 → 强信号，切
  │   └─ 没有 → 弱信号，先观察 3 个月
  │
  ├─ 两边更新频率差 > 5 倍？
  │   ├─ 是 → 切（高频边独立演进）
  │   └─ 否 → 强合弱切
  │
  └─ 切完做 3 件事了吗（覆盖 / 路径 / 统计）？
      ├─ 是 → 落地
      └─ 否 → 回滚
```

**一句话总结**：第二层切分是"读者路径工程"而不是"主题分类学"。先有读者，再有分类。本节自身不创建任何文件——只回答"现在该不该切 / 切什么维度"的问题。
