# ref 路由优化 — 序列化命名模式

> **触发门槛**：ref 数量 > 5。少于等于 5 个时保持平铺命名（如 `沉淀为ref.md`），不为编号而编号。
>
> ref 数量超过 5 后，平铺命名的路由表会退化为无结构清单——读者扫一眼分不出"哪些 ref 属于同一类动作"。本 ref 解决的就是这个问题：**用序列代号给 ref 建立一层"类别索引"**，主文档 ref-map 通过代号即可表达分类。

## 编号规则

格式：`<序列字母><两位序号>-<名称>.md`

```
A00-结构演化路由.md     ← 00 = A 序列元数据
A01-沉淀为ref.md        ← 01 起 = 动作 ref
A02-ref路由优化.md
B00-合并路由.md         ← 00 = B 序列元数据
B01-合并审计.md
B02-合并执行.md
C01-创建新skill.md      ← 单成员序列：00 可省，直接 01
```

| 组成           | 规则                                                                                                | 示例                                 |
| -------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------ |
| 序列字母       | 大写字母，一个序列 = 一个动作类别                                                                   | `A`                                |
| 序号 `00`    | **保留给序列元数据 ref**：该序列的详细 route 信息（序列内信号→成员路由、成员边界、升级路径） | `A00-结构演化路由.md`              |
| 序号 `01` 起 | 动作 ref，按主次/流程顺序递增                                                                       | `A01`、`A02`                     |
| 名称           | 保留语义名，连字符连接；**文件可读性优先，不搞纯代号**                                        | `A01-沉淀为ref.md` 而非 `A01.md` |

**为什么保留原名称**：纯代号（`A01.md`）要求读者先查 ref-map 才知道内容是什么，多一次跳转；代号 + 名称的文件名自带语义，`ls references/` 一眼可读。

**00 元数据 ref 的取舍**：多成员序列（≥2 个动作 ref 且存在边界混淆风险）才建 `X00`；单成员序列（如 C）直接从 `01` 起，不为凑格式造空 ref。元数据 ref 自身**不承载动作 SOP**，只收敛"序列内路由"——它让主文档 ref-map 保持一行一序列的粒度，把"该进序列哪个成员"的判断下沉到序列入口。

## 序列划分原则

**按「读者 / 动作类别」划分，不按主题词划分。**

- 序列 = 一类读者或一类动作。例：A 序列 = 结构演化类动作，B 序列 = 合并类动作，C 序列 = 创建类动作
- 每序列内 `01` 给最高频/主流程的 ref，后续按流程顺序递增
- 判断标准沿用 [[X01-沉淀为ref]] 第二层切分的读者路径判据：**"读这些 ref 的人，会不会因为场景不同而只读其中一个序列？"** 是 → 分不同序列；否 → 塞同序列

**反例**：按文件名字母序编号、按创建时间编号——编号应承载分类信息，不是流水号。

## 子序列（可选，仅限单序列大量膨胀时）

> **默认不用**。顶层 A/B/C 序列区分 ref 已经完全够用；子序列是特例，不是常规层级，平时不为"结构整齐"而开。

格式：`<序列字母><子序列字母><两位序号>-<名称>.md`

```
Aa01-xxx.md     ← A 序列下的子类别 a
Aa02-xxx.md
Ab01-xxx.md     ← A 序列下的子类别 b
Ab02-xxx.md
Ba01-xxx.md     ← B 序列不膨胀，直接 B01 起，无子序列
```

| 组成             | 规则                                                                                   | 示例       |
| ---------------- | -------------------------------------------------------------------------------------- | ---------- |
| 子序列字母       | 小写字母，跟在序列字母后；一字母 = 该序列内的一个子类别                                | `Aa`       |
| 序号 `01` 起    | 子序列内独立递增，与兄弟子序列互不干扰                                                  | `Aa01`     |
| 子序列 `00`     | **不设**。序列级元数据由顶层 `X00` 承担；子序列若也需独立入口，说明它该升级为顶层序列  | —          |
| 名称             | 同顶层规则，代号 + 语义名，文件可读性优先                                              | `Aa01-xxx.md` |

**启用条件（同时满足才用）**：

1. 单个序列的动作 ref 已膨胀到读者一屏扫不完（经验值：该序列 > 8 个动作 ref）
2. 且序列内已出现 ≥2 个清晰的二级动作类别，同一子类别内成员共享读者路径
3. 顶层序列数仍保持 2-4 个，不因引入子序列而超限

**不启用的情况**：

- **按序列独立判断**：只有膨胀的那个序列用子序列，其他序列继续 `B01` 平铺，不强行凑 `Ba01`
- **能升级就不降级**：若膨胀出的部分自成一类动作、读者会整组只读它 → 直接启用新的顶层序列（如 `D`），而不是塞成 `Ab`。子序列只用于"确属同一大类下的细分"
- 数量够不上膨胀阈值 → 保持顶层平铺，子序列一个都不开

**主文档写法**：序列总览的成员列按子序列分组，ref-map 代号列写完整代号：

```markdown
| 代号 | 类别 | 成员 |
| --- | --- | --- |
| A | 结构演化与维护 | [[A00-结构演化路由]]（入口）→ Aa01 / Aa02 / Ab01 / Ab02 |
| B | 合并 | [[B00-合并路由]]（入口）→ B01 / B02（未膨胀，无子序列） |
```

**续号与收拢**：子序列内按 max 序号 +1 续号；成员撤并后在同子序列内收拢重排，不留空洞；子序列清空则小写字母废弃、不复用给新子类别（同顶层字母规则）。重命名仍用 `git mv`，并全量修正 `[[完整代号-原名]]`（含跨 skill 引用）。

## 主文档结构：序列先于 ref 明细

主 SKILL.md 中，**序列图例必须放在 ref-map 明细表之前**——读者先建立"字母 = 类别"的心智映射，再读逐行明细，而不是读完全部明细才回头理解代号：

```markdown
## 序列总览（先读这里）

| 代号 | 类别 | 成员 |
| --- | --- | --- |
| X | 结构演化与维护 | [[X00-结构演化路由]]（入口）→ X01 沉淀为ref / X02 ref路由优化 / X03 内容同步 |
| Y | 合并 | [[Y00-合并路由]]（入口）→ Y01 合并审计 / Y02 合并执行 |
| Z | 创建 | Z01 创建新skill（单成员，无元数据 ref） |

## 场景路由（ref-map 明细）

| 场景 | 信号 | 何时读取 | 代号 | 路径 |
| --- | --- | --- | --- | --- |
| ... | ... | ... | ... | ... |
```

明细表每行的「代号」列与总览表对应；有元数据 ref 的序列，其入口即 `X00` 文件——读者只需记住"进 A 序列先看 A00"。

## 执行 SOP（对已有 skill 做序列化改造）

### Step 1: 盘点与划分

1. 列出 `references/` 全部 ref 及各自职责
2. 按动作类别归组，产出序列划分表（字母 → 类别名 → 成员）
3. 序列数控制在 **2-4 个**：超过 4 个说明分类维度太细，读者记不住字母含义
4. 逐序列判断是否需要 `X00` 元数据 ref（多成员 + 有边界混淆 → 建；单成员 → 跳过）
5. 逐序列判断是否膨胀到需要子序列（条件见上文「子序列」；不膨胀就不开）

### Step 2: 建元数据 ref + 重命名动作 ref

```bash
# 有元数据的序列：新建 X00
# 动作 ref 全部重命名为 X01 起
git mv references/<原名>.md references/<代号>-<原名>.md
```

**注意**：用 `git mv` 保留历史；同批全部重命名，不留半编号半平铺的混合态。

### Step 3: 全量修正 [[链接]]

`[[原名称]]` 链接全部改为 `[[代号-原名]]`，范围包括：

- 主 SKILL.md（序列总览、ref-map、路由优先级、易错表、正文锚点）
- 所有 ref 文件内部互引 + 仓库内其他 skill 的跨 skill 引用

用 Grep 搜旧名确认零残留。

### Step 4: 主文档加「序列总览」+ ref-map 加「代号」列

按上文「主文档结构」模板：序列总览表放 ref-map **之前**。**主文档只加一表一列，不新增场景级章节**——序列信息由代号列和总览表承载，主文档行数不因此增长。

### Step 5: 校验

- [ ] 动作 ref 全部 `X01` 起编号；`X00` 仅用于序列元数据 ref
- [ ] 元数据 ref 只含序列内路由，不含动作 SOP；无空 ref
- [ ] 序列数 2-4 个，每序列有明确类别名
- [ ] 子序列仅在单序列膨胀（> 8 个动作 ref 且出现 ≥2 个二级类别）时启用；未膨胀序列保持顶层平铺，无空壳子序列
- [ ] 子序列不设 `X00`；膨胀部分若自成一类动作，已升级为顶层序列而非 `Ab`
- [ ] 主文档**序列总览在 ref-map 明细之前**，明细表有「代号」列
- [ ] `[[旧名]]` 链接零残留（Grep 验证，含仓库内跨 skill 引用）
- [ ] 主文档未新增场景级章节，仍只含原则 + ref-map
- [ ] 核心流程/触发条件未变

## 扩展时如何续号

- 新 ref 属于已有类别 → 沿用序列字母，取该序列 max 序号 +1（如 A02 之后加 A03）
- 新 ref 属于某膨胀序列内的已有子类别 → 取该子序列 max 序号 +1（如 Aa02 之后加 Aa03）
- 单序列成员持续增多但够不上新顶层类别 → 按上文「子序列」启用小写字母分组；子序列字母同样只增不复用
- 新 ref 是全新类别 → 启用新字母（如 D），动作从 `D01` 起（`D00` 留给潜在元数据）
- **序列收拢（用户指定铁律）**：删除/合并某成员后，**后续成员自动收拢重排**（如 A03/A04 撤并后 → A02/A03），不留空洞跳号；重排用 `git mv` 保历史，并全量修正 `[[代号-原名]]` 链接（含跨 skill 引用），Grep 旧代号零残留才算完成
- 序列字母本身废弃时（整个序列清空）字母才不复用给新类别（避免历史代号指向漂移）
- 序列内成员多到边界频繁混淆 → 说明 `X00` 元数据 ref 需要扩充路由行，而不是继续加成员

## AI 生成代码 Top错误事项(不超过5)

| 错误                                | 后果                                     | 预防                                   |
| ----------------------------------- | ---------------------------------------- | -------------------------------------- |
| ref ≤ 5 也强行编号                 | 编号不承载信息，纯噪音                   | 严守 >5 门槛                           |
| `00` 位误用：动作从 `00` 起 / 单成员序列造 `X00` | 元数据无处安放，或留下空壳 ref 无人读 | `00` 恒为元数据保留位；多成员 + 有边界混淆才建，单成员直接 `01` |
| 未膨胀也开子序列 / 该升级却塞子序列 | 多一层代号要多记一层映射；或大类下挤进异类 | 单序列 >8 且出现 ≥2 二级类别才开 `Aa`；自成一类的动作升级为顶层序列 |

## 本 skill 自身即示范

key_board 已按本模式改造：X = 结构演化与维护（X00 入口 + X01/X02/X03）｜Y = 合并（Y00 入口 + Y01/Y02）｜Z = 创建（Z01/Z02，无元数据）。主 SKILL.md 序列总览在 ref-map 之前。注意：key_board 自身作为元 skill 用 X/Y/Z 与业务 skill 的 A/B/C 区分——业务 skill 自身做序列化命名时仍按 A/B/C 走，与本 ref 教学规则一致。key_board 当前各序列均未膨胀到子序列阈值，故全仓无 `Xa`/`Yb` 这类代号——这正符合"平时不用"。
