# 合并执行 — 4 阶段手册

> 本文档来自原 `merge-skill/SKILL.md`，作为 key_board 在「**合并多个 skill**」这种**特殊优化场景**下的执行手册。
>
> **使用条件**：当用户说"合并 skill"、"创建统一 skill"、"把多个 skill 合成一个"时，本 ref 是 key_board 主流程判断**确需合并后**的操作手册（未指定目标的探索式审计走 [[Y01-合并审计]]）。
>
> key_board 主流程仍负责结构判断（是否真要合并、拆出去不行吗），本 ref 负责**动手合并时的 4 阶段流程细节**。
>
> **变体：并入现有 skill 的 ref（A → B.references/）**：当用户指定"把 A 合并进 B 的 ref"且 B 已有成熟 ref 架构时，走本手册的变体路径——4 阶段不变，但产物不同：
>
> | 阶段 | 标准 4 阶段（A+B → 新 skill C） | 变体（A 并入 B 的 ref） |
> | --- | --- | --- |
> | Phase 1 阅读真实代码 | 两者都做（代码是唯一真相） | 相同 |
> | Phase 2 建主文档 | 新建 C/SKILL.md | **不改 B 主文档骨架**，只在路由表/序列总览加行 |
> | Phase 3 归档 | A、B 原文逐字归档到 C/references/ | A 的场景**重构吸收**为 B 的新 ref（按 [[X02-ref路由优化]] 续号；补跨 ref 链接与细节），非逐字归档 |
> | Phase 4 清理 | 删除 A、B 目录 | 删除 A 目录 + B 的 description 补 A 的触发词 + 清理 A 的外部引用（symlink / 分组配置 / 记忆） |
>
> 变体的核心判断：**重构吸收 > 逐字归档**——逐字归档会把旧 skill 的双角色结构（原则+场景混编）原样带进 B 的 ref 树，违背 B 的架构约定；吸收时按 B 的 ref 模板（frontmatter + 加载时机 + SOP + Top错误事项）重写，并让新 ref 与 B 既有 ref 互相链接。

> **依赖声明**：本 ref 按 [[Z01-创建新skill]] 的两层依赖声明规范执行——`skill-creator` / `writing-skills` 是元层工具（可选辅助，用完即弃，不落盘）；合并产物层通常无依赖。动手前在回复顶部按 Z01 规范分两行声明并校验。

## 核心原则

合并 skill 不是简单拼接，而是：

1. **阅读真实代码** — 确保新 skill 反映最新实现
2. **保留历史参考** — 被合并的 skill 归档到 `references/` 目录
3. **与代码同步** — 文档必须与真实代码一一对应

## 触发条件

- "合并 skill"、"创建统一 skill"
- "把多个 skill 合并成一个"
- "创建 references 目录存放原始 skill"
- "基于真实代码创建新 skill 文档"

## 合并流程

### Phase 1: 准备 — 阅读真实代码

```
任务：理解要合并的 skill 所涉及的真实代码

1. 确定 skill 主题对应的代码文件
   → 使用 Glob 搜索相关代码文件
   → 读取 manifest.json 确认 content script 入口

2. 通读所有相关实现代码
   → 按层级顺序阅读：Layer 1 → Layer 2 → Layer 3 → Layer 4
   → 每个关键函数都要读懂实现逻辑

3. 识别代码与现有 skill 文档的差异
   → 对比：函数名、参数、返回值、流程
   → 标记：缺失的说明、过时的示例、不一致的实现

4. 如果发现 skill 文档与代码不符：
   → 【重要】先按 [[X03-内容同步]] 的 SOP 修正原始 skill 文档使其与代码一致
   → 或者在新 skill 中明确标注"代码已更新"的差异点
   → 绝不能不更正就合并 — 否则错误会被放大
   （Phase 1 的这步就是 [[X03-内容同步]] 事实层的精简版；完整巡检走 X03）
```

**Phase 1 质量检查**：

| 检查项         | 通过标准                          |
| -------------- | --------------------------------- |
| 代码文件完整性 | 所有提到的文件都存在且可读        |
| 函数签名一致   | 文档中的函数签名与代码完全匹配    |
| 示例可运行     | 代码示例复制到 console 能正常执行 |
| 差异已记录     | 每个差异都有明确标注              |

**关键**：不要假设现有 skill 文档是正确的。真实代码才是唯一真相。如果发现问题，先修正再合并。

### Phase 2: 创建新 Skill 主文档

```
任务：基于真实代码创建新的统一 SKILL.md

1. 确定新 skill 名称和目录路径
   → 命名规范：小写字母 + 连字符 (如 video-tracker)
   → 路径：.claude/skills/{新skill名称}/

2. 编写 SKILL.md frontmatter：
   → name：纯小写+连字符
   → description: 触发描述（写触发症状/场景，非内容总结；语言随目标 skill 库惯例，中文库用中文）

3. 编写文档主体结构：
   ├── Overview (核心原理，一句话)
   ├── 触发条件 (症状列表)
   ├── 核心架构 (层级图或流程图)
   ├── 各层实现 (代码示例 + 说明)
   ├── 文件索引 (文档章节 → 真实代码文件)
   └── 参考资料 (references/ 章节链接)

4. 从真实代码提取关键实现：
   → 复制实际代码片段（不是记忆或推测）
   → 添加行号引用便于定位
   → 代码注释保留（说明 Why）

5. 合并多个 skill 的核心概念：
   → 提取各原 skill 的核心概念
   → 按实际代码架构重新组织
```

**Phase 2 质量检查**：

| 检查项           | 通过标准                              |
| ---------------- | ------------------------------------- |
| frontmatter 完整 | name + description 存在且格式正确     |
| description 规范 | 触发描述（症状/场景），非内容总结，语言随目标库惯例 |
| 代码可定位       | 每个代码片段都有文件路径和行号        |
| 层级清晰         | 分层结构与实际架构一致                |
| 无臆测内容       | 所有内容都可追溯到真实代码            |

> 代码片段标注格式：`// path/to/file.js:44-72`（文件路径 + 行号范围）。

### Phase 3: 创建 References 目录

```
任务：将原始 skill 归档为参考文档

1. 创建 references 目录：
   → .claude/skills/{新skill名称}/references/

2. 读取每个原始 skill 的完整 SKILL.md：
   → 读取原始文件内容
   → 保持原有结构不变
   → 在文件开头添加 reference frontmatter

3. 写入归档文件：
   → references/{原始skill名称}.md
   → frontmatter 添加：name: {原始名}-reference, description: Reference — {描述}

4. 在主文档末尾添加"参考资料"章节：
   → 说明原始文档归档位置
   → 列表形式展示：文件名 → 内容描述

> **归档豁免**：归档进 references/ 的历史文件是**历史参考**，不是动作 ref——不进主文档路由表、不需要"加载时机"。key_board 主文档"所有 ref 在路由表登记"的检查清单**不适用**于它们；反之，有动作语义的 ref（变体路径的重构吸收产物）必须按正常 ref 登记。
```

**Phase 3 质量检查**：

| 检查项                | 通过标准                          |
| --------------------- | --------------------------------- |
| references 目录存在   | .claude/skills/{name}/references/ |
| 所有原始 skill 已归档 | 数量与合并的 skill 数量一致       |
| frontmatter 正确      | 每个归档文件有 reference name     |
| 主文档有参考章节      | "参考资料" 章节在文档末尾         |
| MEMORY.md 已更新      | 记忆索引含新 skill 一行           |

> **归档豁免**：归档进 references/ 的历史文件是**历史参考**，不是动作 ref——不进主文档路由表、不需要"加载时机"。key_board 主文档"所有 ref 在路由表登记"的检查清单**不适用**于它们；反之，有动作语义的 ref（变体路径的重构吸收产物）必须按正常 ref 登记。

### Phase 4: 删除原始 Skill

```
任务：清理被合并的原始 skill

1. 最终确认：
   → references/ 中所有原始 skill 已完整归档
   → 新 skill 主文档已验证无误

2. 删除原始 skill 目录：
   → 使用 rm -rf 命令删除整个目录
   → 包括 SKILL.md 和所有子目录

3. 验证删除成功：
   → Glob 确认原始目录不存在
   → 新 skill 目录完整存在
```

**Phase 4 质量检查**：

| 检查项          | 通过标准                               |
| --------------- | -------------------------------------- |
| references 完整 | 所有原始 skill 内容都在 references/ 中 |
| 删除成功        | 原始目录不存在于 .claude/skills/       |
| 新 skill 可用   | 主文档可正常读取                       |
| 目录结构正确    | 只有 SKILL.md 和 references/           |

## 文件索引模板

每个合并后的 skill 必须包含文件索引：

```markdown
## 文件索引（与文档对应的真实代码）

| 文档章节 | 对应文件 |
|---------|---------|
| Layer 1 | `content/videoTracker.js` |
| Layer 2 | `content/content.js` |
| Layer 3 | `background/videoProgress.js` |
| ... | ... |
```

## References 章节模板

```markdown
## 参考资料

原始 skill 文档（已归档至 `references/` 目录）：

| 文件 | 内容 |
|------|------|
| `references/<原skill1>.md` | <原 skill1 的核心内容描述> |
| `references/<原skill2>.md` | <原 skill2 的核心内容描述> |

**说明**：主文档基于真实代码重新编写，合并了各原始 skill 的核心概念，并更正了与实际代码的差异。原始文档保留作为历史参考。
```

## MEMORY.md 更新

```markdown
- [新skill名称](新skill名称/SKILL.md) — 简短描述（含 references/ 说明）
```

## AI 生成代码 Top错误事项(不超过5)

| 错误                    | 后果           | 正确做法               |
| ----------------------- | -------------- | ---------------------- |
| 不读代码直接拼接        | 文档与实现脱节 | 先通读相关代码文件     |
| 删除原始 skill 前未归档 | 历史版本丢失   | references/ 完整后再删 |
| 文件索引不完整          | 读者找不到代码 | 列出所有涉及的代码文件 |
| 复制粘贴不做验证        | 错误示例误导   | 代码必须来自真实文件   |

## 与 key_board 主流程的衔接

key_board 主 SKILL.md 负责**结构判断**（是否要合并、拆出去不行吗），本 ref 负责**动手合并时的执行细节**。

调用顺序：

1. 先走 key_board 主流程 → 判断"合并"确有必要
2. 加载本 ref → 获得 4 阶段合并流程
3. 合并过程中**仍要遵循 key_board 的核心原则**：不主动创建 skill（这次创建新 skill 是合并的副产品）、不修改前置 skill、按主题自然分配内容、不为主文档减肥而硬拆

注意：本 ref 中的"创建新 skill"指的是**合并产生的新 skill**，不是 key_board 的本职动作。未指定目标的探索式审计走 [[Y01-合并审计]]。
