# Z02 — 从代码库创建规范 skill（防腐蚀规范生成）

> **使用条件**：主 SKILL.md 路由确认是「创建」类信号，且来源是**真实代码库**（为某个目录/模块生成规范 skill）。从对话/反思总结创建走 [[Z01-创建新skill]]。
>
> **本 ref 不是特定语言的规范生成器**——分析方法适用于任何技术栈（JS、Python、Go、Rust、Java 等）的任何代码库。

## 触发条件

- "为这个项目创建模块规范" / "分析这个目录"
- "防止代码腐蚀，生成规范 skill"
- "新模块立项，确立编码规范"
- "发现某个目录没有对应 skill"

**归属判定**：创建来源是代码 → 本 ref；创建来源是对话/反思 → [[Z01-创建新skill]]。两者共用 Z01 的**两层依赖声明规范**（元层/产物层），动手前同样分两行声明并校验。

## 核心原则

| 原则 | 说明 |
| --- | --- |
| **从代码出发** | 必须完整遍历目标目录、分析依赖后再写规范，不能凭空编造 |
| **规范可执行** | 检测标准必须给出具体命令或工具，不能写"代码要保持整洁" |
| **不生成孤儿文档** | 每个产出物必须是 `.claude/skills/<name>/SKILL.md`，能被系统发现 |
| **先同步再创建** | 如果已有 skill 与实际代码不一致，先修复（[[X03-内容同步]]）再考虑创建 |
| **语言无关** | 分析方法适用于任何编程语言；语言变体细节放 ref（注意：**方法通用 ≠ 产物通用**） |
| **产物项目级** | 头部声明"仅适用于 <项目>"，路径 / 模块名写真实值——本 ref 的产物使用当前项目的信息。作用域判定见 [[X04-产物作用域]] |

## 创建流程

### Step 0: 声明作用域（本 ref 的产物**默认项目级**）

从代码库创建的规范 skill 要在**本项目内可执行**，因此：

- 头部必须声明适用范围：`> 本 skill 仅适用于 <项目/仓库>。`
- 路径 / 模块名 / 类名写**真实值**，不要用 `<模块名>` 占位符糊弄
- **但分析方法保持语言无关**（Step 1-2 的侦察与依赖分析命令要能套用到任何技术栈）

> 关键区分：**方法的通用 ≠ 产物的通用**。方法语言无关，产物默认项目级、使用当前项目的信息。判定细节见 [[X04-产物作用域]]。

### Step 1: 侦察——遍历目标目录

```bash
# 获取所有源文件（根据实际扩展名调整）
find <target-dir> -type f \( -name "*.js" -o -name "*.py" -o -name "*.go" -o -name "*.rs" \) | sort

# 文件大小排行（识别过于臃肿的文件）
find <target-dir> -type f -name "*.java" -exec wc -l {} + | sort -rn | head -20
```

分析维度：

| 维度 | 说明 |
| --- | --- |
| 文件数量 | 判断模块复杂度 |
| 文件大小 | 超过 300 行标记为过大文件（阈值可按语言调整） |
| 命名模式 | 识别模块划分（`models.py` + `views.py` / `<name>.service.ts` 等） |
| import/依赖图 | 识别职责边界和耦合程度 |

### Step 2: 分析——模块依赖

```bash
# 导入分析（适配目标语言的 import 语法）
# JS/TS:  import ... from '...'
# Python: import ... / from ... import ...
# Go:     import "..."
# Rust:   use ...
grep -rn "^import\|^from.*import\|^use " <target-dir>/ --include="*.py" --include="*.rs" | sort
```

生成依赖矩阵：

```markdown
## 依赖矩阵

| 文件 | 导入/引用的模块 | 被引用次数 | 行数 | 状态 |
|------|---------------|----------|------|------|
| main.py | config, utils | 0 | 50 | ✅ |
| config.py | (无) | 5 | 80 | ✅ |
| models.py | utils, db | 3 | 350 | ⚠️ 过大 |
```

### Step 3: 执行——输出 SKILL.md

目录结构：

```
.claude/skills/<模块名>/
├── SKILL.md        ← 必选
└── references/     ← 可选（仅当有独立引用价值的子主题）
```

文件模板（语言无关）：

```markdown
---
name: <模块名>-standards
description: <触发描述>
---

# {项目} {模块} 模块规范

## 职责边界
| 文件 | 职责 | 禁止混入 |
|------|------|---------|
| main.py | 入口/组装 | 业务逻辑 |

## 正反案例
### bad_example
[错误的代码模式]
### good_eg
[正确的代码模式]
```

### Step 4: 验证

```bash
# 验证所有引用的文件存在
grep -oP '[\w/.\-]+\.[a-z]+' .claude/skills/<name>/SKILL.md | while read f; do
  [ -f "$f" ] && echo "✅ $f" || echo "❌ $f"
done

# 验证所有引用的类/函数存在（适配语言关键字）
grep "class AClass\|struct AStruct" $(find . -name "*.py" -o -name "*.go")
```

## 创建之后

- 规范 skill 的**长期维护**进入 X 序列：代码改动后同步 [[X03-内容同步]]、使用后经验沉淀（同在 [[X03-内容同步]] 经验层）、ref 结构演化 [[X00-结构演化路由]]
- 可选：调用 `skill-creator` 写 2-3 个触发测试用例、优化 description 提高触发精度

## 错误案例

| 错误操作 | 实际后果 | 正确做法 |
|---------|---------|---------|
| 生成独立的 .md 文档而非 SKILL.md | 文档无法被系统发现，成为孤儿 | 只产出 `.claude/skills/<name>/SKILL.md` |
| 不读代码就写规范 | 规范与实际脱节 | 先完整遍历目录 |
| 只看文件名判断职责 | 误判模块边界 | 分析 import/依赖图 |
| 写死语言特定语法 | skill 无法复用于其他项目 | 保持语言无关，或通过 references/ 分语言变体 |
| 在两个 skill 中定义相同规则 | 规则冲突，用户困惑 | 规则唯一定义在归属最近的 skill 中 |

## 成功标准检查清单

- [ ] 读取了目标目录**所有**源文件
- [ ] 生成了模块依赖矩阵
- [ ] 识别了代码异味（过大文件、重复代码、职责混杂）
- [ ] 规范包含**可执行**的检测方式
- [ ] 只产出 `.claude/skills/<name>/SKILL.md`
- [ ] 给出了正反案例（bad_example / good_eg）
- [ ] 验证了所有 import/引用路径正确
- [ ] 不存在两个 skill 定义相同规则
- [ ] 分析方法语言无关（侦察 / 依赖分析可套用其他技术栈）
- [ ] 产物作用域已声明：头部写明"仅适用于 <项目>"，路径 / 模块名用真实值（见 [[X04-产物作用域]]）
