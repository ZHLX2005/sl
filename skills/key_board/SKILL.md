>
> **产出物作用域注意（横切红线）**：任何**要写 skill 内容**的动作（创建 [[Z01-创建新skill]] / [[Z02-代码库创建skill]]、沉淀 [[X01-沉淀为ref]]）动手前，先按 [[X04-产物作用域]] 判定作用域——**通用级零项目上下文（一律不使用当前项目的信息），项目级才使用当前项目的信息且必写真实路径**。出现「局部项目概念或来源」却又是通用 skill = 作用域错配。

## 路由优先级（最重要）

**先扩展现有 ref，无相关主题才创建新 skill。**

处理一个用户信号时按顺序判断：

1. 信号是否匹配上表 X01 / X02 / X03 / X04 / M01 / Y01 / Y02 / Z02 任一？
   - **是** → 加载对应 ref 走 SOP；不要触发创建；不确定进序列哪个成员时先读该序列的 `X00` 元数据 ref
   - **否** → 进入第 2 步
2. 是否需要新增 ref 来承载这个场景？
   - **是** → 走 [[X01-沉淀为ref]] 的「批量模式」或扩展现有 ref 树（ref 总数 > 5 时按 [[X02-ref路由优化]] 分配代号）
   - **否**（这是全新的、独立的主题） → 按创建来源分流：对话/反思 → [[Z01-创建新skill]]；真实代码库 → [[Z02-代码库创建skill]]

> **为什么有这个优先级**：通用总结反思更新同步 skill 的本职是**让现有 skill 体系持续演化**，不是无脑制造新 skill。新增 ref 是「体系内演化」（低成本），创建新 skill 是「体系外扩张」（高成本）。先内后外。

## 平面扩展原则

**主 skill 只负责路由，不负责具体处理场景。**

- 主文档只含：触发条件与路由表（合一）+ 序列总览 + 路由优先级 + 主流程骨架。任何场景的执行细节一律在 references/
- **扩展模式固定**：新场景 → 新建 ref 文件 + 路由表加一行，主文档不加章节、不长胖
- 主文档行数不随场景数增长；ref 数量可以无限扩展
- ref 总数 > 5 时启用序列化命名（见 [[X02-ref路由优化]]）：`X00` = 序列元数据，动作 `X01` 起；主文档靠「序列总览」+「代号」列承载分类

## 核心原则

**主 SKILL.md 负责原则和 ref-map；references/ 才存放具体场景。**

| 文档 | 角色 | 只放 | 不放 |
| --- | --- | --- | --- |
| 主 SKILL.md | 原则 + ref-map | 触发条件、序列总览、路由优先级、主流程骨架、检查清单、路由表 | 任何场景级细节 |
| references/X00-*.md | 序列元数据 | 序列内信号→成员路由、成员边界、升级路径 | 动作 SOP（那是成员 ref 的事） |
| references/<XN>-<名>.md | 具体动作 SOP | 某动作的完整 SOP、示例、正反例、判定细节 | 通用原则（那是主文档的事） |

**演化反模式**：v1 把场景内容全写在主文档是合理的（还没有 ref）；一旦某主题拆出 ref，主文档旧内容必须**同步清空**，原位置只留一句原则 + `[[锚点]]`。否则主文档兼具"场景承载 + ref-map"双角色，行文混乱。主文档随 ref 增多而**变薄**，不是变厚。

### 产出物作用域红线（横切：任何写 skill 内容的动作都先过）

**skill 是有作用域的：通用级不使用当前项目的信息，项目级才使用当前项目的信息。** 写下任何一句内容前先答一个问题——"换个项目 / 换台机器，这句还成立吗？"

| 作用域 | 判据 | 内容要求 |
| --- | --- | --- |
| **通用级** | 换个仓库 / 机器 / 同事，仍然成立 | **零项目上下文**：无项目名、绝对路径、人名、内部术语、**来源句**；需要举例时用 `<占位符>` |
| **项目级** | 脱离这个项目就没有意义 | **使用当前项目的信息**：头部声明适用范围，路径 / 模块名写真实值——占位符在这里等于没写 |

> 出现「局部项目概念或来源」却又是通用 skill → 作用域错配，是最高频的产出缺陷。判定三连问、两条红线、反例、检查清单见 [[X04-产物作用域]]。**创建（[[Z01-创建新skill]] / [[Z02-代码库创建skill]]）与沉淀（[[X01-沉淀为ref]]）动手前必读。**

### 边界

| 不做什么 | 做什么 |
| --- | --- |
| ❌ 不无脑创建新 skill | ✅ 路由优先级保证先扩展 ref |
| ❌ 不改其他 skill 的核心流程/触发条件（除非用户授权） | ✅ 按主题把 skill 组织成 主文档 + 特化 ref |
| ❌ 不动 skill 的代码实现 | ✅ 只搬文档结构 |

## 主流程骨架（5 步）

1. **识别作用域**：用户信号是什么？目标对象是哪个 skill（创建新 skill 时无对象）？有无不可动章节？
2. **路由判定**：按触发条件表查 → 是否匹配现有 ref？走第 3 步（执行）或第 4 步（先评估优先级）
3. **设计方案**：加载对应 ref，按其设计要点出方案（ref 名称、路径、加载时机、为何是独立主题）。**先声明产出物作用域**（通用级 / 项目级，见 [[X04-产物作用域]]）——它决定后面每一句内容怎么写
4. **执行**：按 ref 的 SOP 执行。共同骨架 = 完整迁移内容 → 原位置留 `[[锚点]]` + 一句总结 → 路由表登记。**下沉必须彻底**
5. **校验**：对照 ref 内的检查清单逐项过

## 易错和坑（高频 6 条）

| 错误 | 根因 | 预防 |
| --- | --- | --- |
| 看到「总结成 skill」就无脑走创建 ref | 没看路由优先级 | 必须先查现有 ref 是否可扩展 |
| 顺手改了目标 skill 的核心流程/触发条件 | 越权润色 | 本 skill 只做结构，核心流程禁止动 |
| 把元层依赖（skill-creator / writing-skills）写进新 skill | 两层依赖合并 | 见 [[Z01-创建新skill]] 的依赖声明规范 |
| 把主流程骨架拆进 ref | 误以为所有内容都可沉淀 | 主流程、触发条件、检查清单必须留在主文档 |
| 拆完忘记登记路由表 | ref 成为孤儿文档 | 每建一个 ref 立即在路由表登记"何时读取"；ref 总数 > 5 时同步按 [[X02-ref路由优化]] 分配代号 |
| 通用 skill 里写进项目名 / 绝对路径 / 来源句 | 没判产出物作用域 | 动手前过 [[X04-产物作用域]]：通用级零上下文，项目级才用项目信息 |

## 成功标准检查清单

- [ ] 路由优先级被遵守（先扩展 ref，无相关主题才创建）
- [ ] 主 SKILL.md 只含原则与路由，无场景级内容残留
- [ ] 主题在主文档和 ref 之间分配清晰、不重复
- [ ] 所有 ref 在「触发条件与路由表」登记，且写明"何时读取"
- [ ] `[[ref-name]]` 链接与文件名一一对应（启用序列化后为 `[[代号-原名]]`，X00 为元数据 ref）
- [ ] 目标 skill 的核心流程/触发条件未变（除非用户授权）
- [ ] 产出物作用域已声明：通用级未使用项目信息（零上下文），项目级使用了真实路径（见 [[X04-产物作用域]]）
- [ ] 没有空 ref 文档
- [ ] 用户确认了拆分方案（如未明确授权）

## 何时**不**触发本 skill

- 用户想**改 skill 的代码/实现** → 本 skill 不管代码
- 用户想**优化触发描述 / 评估 skill 效果** → `skill-creator` 的 description 优化 / eval 流程
- 目标 skill 无独立主题且不需创建 → 不要硬拆，劝退

## 与其他 skill 的协作

```
key_board        →  skill 生命周期管理（路由 + 11 ref SOP，4 序列：X 结构演化与维护 / Y 合并 / Z 创建 / M 质检；业务 skill 自身用 A/B/C 序列，二者不撞名）
skill-creator    →  评估/优化/打包 skill (质量保障)
```

本 skill 是 skill 体系的"路由器 + 演化执行器"；`skill-creator` 是"质量评估与优化器"。两者职责不同，不重叠。
